# Rendering

A spec draws the same picture on screen, as SVG or PNG, headless in Node, and in other viewers. Three public forms sit
between the spec and the pixels, and each one is a place another renderer can attach.

```
spec ─resolve─▶ resolved view ─layout─▶ draw lists ─▶ backend: Canvas2D · SVG · PNG · recording · yours
 │                    │
 │                    └─ other viewers that want Seq*'s meaning (maps, themes, fallbacks resolved)
 └─ other viewers that map the language onto their own model (documented by the language reference)
```

- **The spec**, documented by the language reference. A viewer can map the language onto its own model, as a JBrowse
  converter did.
- **The resolved view**. Refs are followed, defaults filled, maps resolved, themes turned into values, and each layer's
  fallback chain listed. It holds no data, no pixels, no fonts and no target, so it is the same for every renderer.
- **Draw lists**. The resolved view is laid out for a size, a viewport and a target (which picks each layer's first
  drawable fallback), from the data store's entries, as typed primitives in passes. Hit-testing reads the same layout.
- **Backends** draw the draw lists. Canvas2D draws on screen; SVG is a string with no DOM; PNG comes from either; a
  recording backend serves tests. An application can add its own.

## Headless

The core and the SVG backend run in Node. Text metrics are a port: the browser measures with a canvas, and Node uses a
bundled table, so the layout matches. `renderSvg(spec, options)` and a command-line renderer turn a spec file into SVG
or PNG, so another viewer's picture can sit beside Seq\*'s without writing code.

## One picture

The Canvas2D and SVG backends draw the same draw lists, so they differ only in rasterization. Tests compare their
recorded calls, and visual tests compare their pixels.
