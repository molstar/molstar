# Agent interface rules {#agent-interface-rules}

How agents learn the system (skills) and act on it (tools). → [§skills-and-tools](sketch-patterns/skills-and-tools/README.md)

## In brief

**Skills explain domains** (§skills). A skill explains one domain to an agent; skills are discoverable with progressive
disclosure (index first, detail on demand; what decides *whether* an agent acts goes in the always-disclosed prompt,
skills teach *how*), dynamic where the system is, small and stable, tested like code (their
examples run), and searchable.

**Tools: a small, stable surface** (§tool-surface).
- Two tools per domain, `<domain>_read` and `<domain>_write`, taking expressions in the domain's language rather than
  bespoke parameters, plus one system-wide `skills_read` (`(index)`, `(skill …)`, `(search …)`); the surface never
  changes shape as the domain grows.
- `_read` never mutates; `_write` goes through the command policy, supports dry-run and is recorded. The edge is forgiving (repairs slips) and honest (says what it repaired). Refusals say whether a retry can
  help, which layer refused and, when known, a corrected form `(try ...)`; after a non-retryable refusal, stop and report.
- Results are compact representations within a budget; batch to save round trips. Large representations are read
  outline-first (records with locators and hashes) and drill down: a derived record names its basis, followed one step
  at a time to the source. Records carry affordances, the commands the requester may run on them, prefilled (the bulk
  form for many writes, addressable parts named), so agents copy forms instead of guessing them.
- One tool layer, many transports (in-process, HTTP, MCP); cross-domain work goes through locators.

**Coordination is a domain** (§agent-communication). Agents coordinate in a shared representation, not private chat: they declare plans
before acting, plans are queryable, claims are leases, messages are typed, addressed and structured, an inbox is a
query, people are participants, every action is least-privilege and recorded. Floor control (who answers, when an agent
stays silent, how many agent-to-agent turns) is decided by rules or a gate, not by each agent's prompt.

## Skills: how things work {#skills}

1. **A skill explains a domain to an agent**: {#skill-explains-domain} its concepts, vocabulary, query languages and dialects, commands, typical workflows, pitfalls and short examples. There is one skill per domain (a representation or module: `doc`, `scene`, `mol`, `data`, `sem`, ...), plus one small entry skill for the system as a whole.
2. **Skills are discoverable, with progressive disclosure.** {#discoverable-skills} Only an index (name and one line per skill) is always in context. The agent loads a skill when it needs it, and a skill points to deeper material (sections, examples, registry queries) instead of including it. What decides **whether** an agent acts at all (that it may keep notes beyond this conversation, when to act on a document unasked, to read outlines first) belongs in the always-disclosed prompt or a core skill (agent-harness's `agent-definition` (not adopted here)); an on-demand skill teaches **how**, and an agent that does not know a capability exists never loads the skill that describes it.
3. **Skills are dynamic where the system is.** {#dynamic-skills-follow-system} Anything that a registry knows (commands, error codes, languages, dialects, concepts, spaces; §stable-error-codes, §command-reachable, §query-languages, §semantic-concepts) is generated from the running system or read through the domain's read tool (`(help ...)`), so a skill cannot drift from the code. The static parts (narrative, workflows, pitfalls) are files kept beside the module. The rules are referenced, never copied (§rules-are-source).
4. **Skills are small and stable.** {#small-stable-skills} A skill fits a modest context budget (§context-budget) and says what to read next. Content that changes often lives behind the read tool, not in the skill text, so a long-running agent context does not keep acting on stale copies.
5. **Skills are tested like code.** {#skills-tested} Their examples run through the real tools (§tool-surface) at the gate (§the-gate): every example form parses, every command and function it names exists, and its output matches.
6. **Skills are searchable.** {#searchable-skills} Besides the index, `skills_read` takes `(search "<text>")` and returns a short ranked list of matches with locators into skills, sections, commands, functions, concepts and error codes, so an agent that does not know a name can still find it. Fuzzy lexical matching (typos, partial names, synonyms declared in the registries) is the default; semantic search (embeddings) is an optional backend behind a search port, added when lexical search is not enough, and the tool surface does not change when it arrives (§fixed-tool-shape). Search indexes are derived from the same registries as `(help ...)`, never maintained by hand.

## Tools: a small, stable surface {#tool-surface}

1. **Two tools per domain: `<domain>_read` and `<domain>_write`**, {#read-write-tools} plus a system-wide `skills_read` for the index and skill content. A typical system has 5-15 tools in total.
2. **Tools take expressions, not bespoke parameters.** {#tools-take-expressions} Each tool takes one string: a form in the domain's languages (S-expressions by default; the JSON spelling of the same tree is accepted, §one-recursive-form). `_read` accepts queries (§query-languages), point reads by locator (§locators), read-only commands and `(help ...)`; `skills_read` accepts `(index)`, `(skill ...)` and `(search ...)` (§searchable-skills). `_write` accepts mutating commands (§command-reachable) and operations (§ops-address-by-id).
3. **Why small**: {#why-small} tool definitions are sent with every request, so a large surface spends context on every turn, and an agent context is append-only: a tool added, removed or changed mid-session leaves earlier turns describing a surface that no longer exists. With a fixed surface, the system's capabilities change as *data* (new commands, functions and concepts, discoverable through `_read`) instead of as tool schemas.
4. **The tool surface never changes shape.** {#fixed-tool-shape} Tool names and their single-string input are permanent; evolution happens in the vocabularies behind them, which are versioned (§data-described-commands, §versioned-representations).
5. **Effects are explicit.** {#explicit-effects} `_read` never mutates and is safe to auto-approve. `_write` goes through the command policy (least privilege, confirmation for destructive commands, §least-privilege), supports `(dry-run <form>)`, and is recorded (§recorded-invocations).
6. **The edge is forgiving and honest.** {#forgiving-honest-edge} Inputs are parsed leniently with reported repairs (§parser-repairs-slips); results echo the normalized form; errors are coded with actionable hints (§actionable-hints), so the agent can correct itself in one step. A refusal states whether retrying can help (`retryable`), which layer refused (enforce, policy, validation; named unless that leaks, §explainable-decisions) and, when one exists, a corrected form (`(try <form>)`). A non-retryable refusal ends the attempt: the agent reports instead of trying other spellings.
7. **Results are compact representations with a budget.** {#compact-results} Results are S-expressions with stable locators (§locators); large results are summarized with a count and a cursor (`(more <cursor>)`) instead of being dumped; every read honors the query context's limits, deadline and cancellation (§query-context, §cancelable-queries).
8. **Batch to save round trips.** {#batched-calls} One call may carry several forms. For reads, `(do f1 f2 ...)` evaluates them in order against one snapshot. For writes, `(tx ...)` is a transaction (§transaction-is-data): all or nothing, steps may use earlier results, one commit and one undo step (§transient-overlay).
9. **One layer, many transports.** {#one-layer-many-transports} MCP, CLI, in-app dev tools and tests are adapters over the same read/write dispatch on top of the command registry and query languages (§near-native-agent-access). Nothing is reachable through a transport that is not reachable through the tools.
10. **Cross-domain work goes through locators.** {#cross-domain-locators} A result from one domain is a locator another domain's tools accept, and `sem_read` converts between spaces (§mappings), so domains stay separate tools without becoming silos.
11. **Reads of large representations are outline-first.** {#outline-first-reads} The default read of a document returns an outline (one record per block or concept instance: kind, locator, a short excerpt, status, value hash); content is read by selection, within a budget (§compact-results, agent-harness's `context-management` (not adopted here)). Records carry hashes, so a follow-up read asks for changes and a write names the version it was made against (meso's `conditional-writes` (not adopted here)). **Reads drill down:** a record that is derived (a summary, a chart, a computed value, a search hit) names its basis by locator, following the derivation's provenance (meso's `provenance` (not adopted here)), and the next read takes one step toward the source within the same budget, until the agent sees the values a person sees; an outline line that cannot be followed is a dead end for the agent. → [meso's `documents` (not adopted here)](../../oz/representations/README.md)
12. **Results carry affordances.** {#affordances} A record lists the commands the requester may run on it (policy-filtered, §one-policy-port), with arguments prefilled from the result, as the command palette does for a selection (§command-palette). An agent copies a form it was handed instead of composing one from a schema; an empty list says, before any attempt, that nothing may be changed there. Where a task needs many writes, the affordance offers the bulk form (one write for a whole structure) and names the addressable parts (a table's cells), so the agent neither loops over guessed addresses nor stops half done.

## Agent communication: plans, claims and messages as a domain {#agent-communication}

How agents (and people) coordinate. The protocol is not a new mechanism: it is one more domain, `agent`, with its own representation, query language and commands, reached through `agent_read`/`agent_write` and streamed like any document. → [§agent-protocol](sketch-patterns/agent-protocol/README.md)

1. **Coordination happens in a shared representation, not in private chat.** {#shared-coordination} Agents, users, declared plans, claims and messages are entities in an `agent` tree (§declarative-representations) with ids and links (meso's `graph-links` (not adopted here)), changed through ops (§ops-address-by-id), persisted and streamed like any document (meso's `encodings-and-storage` (not adopted here)). Communication costs two tools, not a new channel.
2. **Agents declare plans before they act.** {#declared-plans} A plan is a goal plus a checklist of steps; each step has a title, a status (`pending`, `in-progress`, `done`, `blocked`, `skipped`, `failed`), the locators it expects to read and touch (§locators), and optional ordering links to other steps. The agent keeps statuses current as it works and revises the plan openly (edits are ops, so the history shows what changed). A plan states intent; it is not a contract for exact actions.
3. **Plans are queryable across domains.** {#queryable-plans} Because steps carry locators, "who is about to change chain A", "which steps are blocked" and "what did this agent finish today" are queries (§query-languages), not log scraping. Overlap between plans is found by intersecting locators through the semantic graph (§mappings).
4. **Claims are leases.** {#claims-are-leases} Before changing a shared target an agent may claim it: a claim names locators, a holder and an expiry and is renewed by heartbeat; an expired claim is void. Claims are advisory coordination; correctness still comes from conditional commits and conflict codes (meso's `conditional-writes` (not adopted here)).
5. **Messages are typed, addressed and structured.** {#typed-messages} A message has a sender, recipients (an actor, a role or a topic), a kind (`ask`, `answer`, `inform`, `handoff`, `review`, `approval`), an optional reply-to, and a body that is a form in the domains' languages (locators, queries, plan steps, dry-run results). Free text is allowed, but never instead of a structured form that exists. Asks have deadlines and expire with a code.
6. **An inbox is a query.** {#inbox-is-query} An agent subscribes to a query over the agent domain (`(msgs (to me) (unanswered))`, `(steps (touches-overlaps <my claims>))`) and receives results as a stream (meso's `framed-protocol` (not adopted here)); there is no separate notification system.
7. **People are participants.** {#people-participate} Users are actors in the same protocol: approvals (the confirmation of §least-privilege, which answers a harness yield, agent-harness's `harness-yields` (not adopted here)), answers and plan edits are messages and ops like any other, and the UI renders plans as checklists from the same representation (§frontend-state).
8. **Least privilege and a full record.** {#least-privilege-full-record} Each participant has an id, a role and a policy (§least-privilege): agents write only their own plans, claims and messages. The domain is persisted with its op log (meso's `tree-store` (not adopted here)), so sessions can be audited, resumed after a crash (an agent reloads its plan and claims) and replayed in evals (§evals).
9. **Floor control is explicit.** {#explicit-floor-control} When several agents share a room or thread, who answers a person and when an agent stays silent is decided by rules or a gate (agent-harness's `admission-and-floor-control` (not adopted here)), not left to each agent's prompt, and agent-to-agent exchanges are bounded so a person stays in the loop.
