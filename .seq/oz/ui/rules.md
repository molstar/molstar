# UI rules {#ui-rules}

Frontend state and logic, the design system and Storybook. Storybook stands for the project's component workbench;
the rules and patterns name it because it is the example they use.

A project may keep look-and-feel patterns in its instance, built on these rules.

## In brief

**State and logic** (§frontend-state).
- The view library is only a view layer: no application state, no business logic; only transient local UI state (hover,
  focus, open, a draft before commit).
- State lives in nested reactive models connected to the backend through API surfaces (§api-boundaries). A model's state is one
  aggregate with atomic updates, never a cell per field.
- UI actions are methods on models backed by commands, as bound closures with stable identity (`onPress={model.save}`).
- Bindings re-render only on relevant change and never own model lifetime; the only view-library glue is one package
  (`useObservable`, `useReactiveModel`).
- The UI never assumes where work runs and stays responsive (main-thread slices well under a frame, ~16 ms, never a
  long task of 50 ms+; long work elsewhere).
- Optimism comes from the shared replica (§optimistic-transactions): every view shows a pending change at once and drops it together.
- Streaming content and its committed form are one item under one id from the first delta.
- A command palette (⌘K) lists the registry's commands for the current context, policy-filtered; never hand-listed.
- Every app has a headless mode: its models without the view layer, on the same ports (§headless-mode).

**Design system and Storybook** (§design-system).
- One token-driven design system (tokens once, emitted as CSS variables; scoped styles such as CSS Modules; no raw values in components).
  Design-system components are presentational: props in, events out, no models.
- Icons: one open icon set (Lucide, say), plus custom icons drawn in its format and guidelines, as
  data in one registry (`lib/icons`) rendered by one `Icon` component; never pasted SVG.
- One top-level Storybook aggregates every package's stories by section; each package declares its sidebar title in its manifest (no folder
  paths in the sidebar). It is the workbench: every shared component has stories for its states (empty, loading, error, long, dense,
  disabled, narrow). Stories run on the real architecture: presentational = props; connected = model on `local()`.
- Reference mocks (hardcoded data, ad-hoc styling, no models) live in a prototype package `prototypes/<design>-reference/`,
  shown under `Reference/`, each naming its `.design/` file; nothing imports them; deleted once folded in.
- Stories are tests (interaction, a11y, visual baselines); a new visual is also looked at once, rendered. Storybook is also the docs hub, rendering docs from their
  source (`_spec/`, `.design/`, registries, these rules), never copies.

**Views are representations** (§views). A view = query + layout intent + view state, stored as data, steered by view
commands (agents only for the viewer who directed them; requested changes apply, others follow the consent model of
§one-consent-model); surfaces are executors;
views are reproducible, load by level of detail, and can be generated. Model and view state are reconstructible from
data (§reconstructible-state), so a screen can be rebuilt where an agent left it.

## Frontend state and logic {#frontend-state}

1. **The view library (React etc.) is a view layer.** {#thin-view-layer} It owns no application state and no business logic. It may own **transient, local UI state** (hover, focus, open/closed, scroll, animation, a text box's draft before it is committed) that only this component needs while it is on screen. Anything that executors, agents or other views must see, or that must be saved, shared, replayed or driven by a command, belongs in a model; a drag or draft that previews a document change is a model overlay (§transient-overlay). Where state lives overall: §three-state-places. Do not create a model just to hold a hover flag. Design-system components are presentational (props in, events out, no models); only feature/container views connect to models.
2. **State lives in nested reactive models**, {#nested-models} tied to the backend through the API surfaces (§api-boundaries). → [§reactive-models](bootstrap-patterns/reactive-models/README.md)
3. **UI actions are methods on models**, {#actions-are-methods} backed by commands (§command-reachable). Simple actions are **bound closures** with stable identity, so a view passes them directly (`onPress={model.save}`) instead of wrapping them in inline lambdas. Actions take only the arguments the UI naturally provides; the view adapts event objects.
4. **Bindings re-render only on relevant change, and never own model lifetime.** {#relevant-rerenders} A component re-renders when the slice it uses changes, not when it subscribes or when unrelated state changes; the view mounts/unmounts a model's activity, while the model's creator owns its disposal; hidden UI does no updates. → [§reactive-models](bootstrap-patterns/reactive-models/typescript.md#react-as-a-view-layer-only)
5. **A model's state is one aggregate with atomic updates**, {#atomic-model-state} not a reactive cell per field: fields that change or are read together live together, one change is one emission, observers never see half-applied changes, and snapshots are never mutated. Independent concerns get their own nested models. → [§reactive-models](bootstrap-patterns/reactive-models/typescript.md#state-is-an-aggregate-not-a-cell-per-field)
6. **The UI never assumes where work runs.** {#location-agnostic-ui} Compute backends are ports (§interface-boundaries) and executors are chosen at composition (§executors-by-composition): a GPU renderer, a worker, the main thread or a remote service.
7. **The UI stays responsive at all times.** {#responsive-ui} Main-thread work is chunkable and yields often enough that input and rendering are never visibly blocked (slices well under one frame, ~16 ms; never a long task of 50 ms+). Long work goes to another backend (§location-agnostic-ui) or is split into cooperative chunks. Exceptions are extremely rare, justified in a comment, and bounded. → [§reactive-models](bootstrap-patterns/reactive-models/typescript.md#keeping-the-main-thread-responsive)
8. **Optimistic updates come from the shared store, never from a component or a single model.** {#optimistic-from-store} A user action submits a transaction (§optimistic-transactions); the replica applies it to the store everything reads, so every view shows it at once and drops it together on rejection. Models show pending and failed state from the transaction status, not from flags they set themselves, and never hand-write a rollback. → [§transactions](../representations/bootstrap-patterns/transactions/README.md)
9. **Streaming content and its committed form are one item.** {#streaming-is-one-item} Anything that streams and then commits (a model's message, a tool's output, an upload, a generated image) has a stable id from its first delta, the same id it is committed under. The UI keeps one item per id whose state moves in place: streaming, committed, failed; the committed version replaces the streamed one in the same update, never appears next to it, and does not re-layout, re-animate or move the scroll position. Two sources (a live overlay and the committed store) showing one thing are merged by id in the model, as `effective = committed ⊕ overlay` (§transient-overlay), never in the component. Rendering stays stable while streaming: incomplete structure (an open code block, a half table) renders tolerantly instead of flickering between layouts. Where the document's collaboration strategy merges small writes cheaply (a CRDT, §collaboration-adapters), a stream may also be written straight into the shared document under its stable id, which gives one item by construction; the item then carries a streaming status until it is finished.
10. **Every action is reachable from a command palette.** {#command-palette} One keyboard entry (⌘K / Ctrl+K) lists the commands of the command registry (§registry-is-spec) that apply in the current context (the selection, the open document, the focused panel), filtered by the policy before they are shown (§one-policy-port), with their arguments prefilled from the context and a dry-run preview where the command has one. The palette is generated from the registry, not hand-listed, so a new command appears in it without UI work.
11. **Every app has a headless mode.** {#headless-mode} Its reactive models run without the view layer, composed on the same ports (`local()` or a test composition), driven through the same model methods and commands, and observed through the same state. Tests, agents and tools use the app this way; the view layer only renders it. Nothing a model needs lives in a component, so the headless app is the whole app minus pixels.

## Design system and Storybook {#design-system}

1. **A single design system.** {#single-design-system} UI is built from a shared component library driven by **design tokens** (color, type, spacing, motion, elevation) defined once in the common layer. Product UIs compose these components and add no private styling primitives; a new visual need becomes a token or component first (§promote-on-reuse). Styling uses **scoped styles** (CSS Modules in the examples) with tokens as CSS custom properties; global CSS is only tokens, a reset and base typography; no runtime CSS-in-JS in shared components (allocation and render cost, §performance); inline `style` only for genuinely dynamic values. → [§design-system-storybook](bootstrap-patterns/design-system-storybook/README.md)
2. **Storybook (or equivalent) is the workbench, one per repository.** {#storybook-workbench} A single top-level Storybook aggregates the stories of every package by section. The sidebar is organized for readers, not by folder paths: each package declares its place once in its manifest (e.g. `"storybook": { "title": "Design system/Components" }`), titles below it come from the file name and an optional short story title, and folders such as `src/` or `stories/` never show. Sections in order: docs, reference, then one per product or prototype, grouped by what readers look for (design system, app screens, flows, internals). A new package appears without editing the Storybook config. Every shared component has stories covering its states (default, empty, loading, error, long content, dense, disabled, dark/light, narrow). Design iteration (§design-plan-implement, §iteration) starts here: a new UI is explored as stories before it is wired into the app. Stories are the visual contract; reviewers and agents judge a component by its stories.
3. **Stories run on the real architecture** {#stories-on-real-architecture} (the exception is the reference section, §reference-mocks). A presentational component's story is just its props; a connected view's story is a **model (or a state representation, §declarative-representations) plus a view** on the in-memory composition (`local()`, §compositions-are-values). No story needs a backend.
4. **Reference/mock section (design-time, temporary).** {#reference-mocks} A clearly separated reference section holds mocks and sketches made during design, kept in a prototype package of their own (`prototypes/<design>-reference/`, outside the build) that Storybook aggregates under `Reference/`: hardcoded data, ad-hoc styling, no models or ports. It is the in-repo prototype space for UI (§iteration).
   - Each reference entry names the `.design/` document it belongs to; a light check fails the merge if that design does not exist.
   - Nothing in the app or shared packages imports from a reference package; it is excluded from app builds and from the baselines of real components.
   - Entries are *folded in* (real components, tokens and stories are built from them) and then **removed** as a checklist item of that work (§design-plan-implement); the design then links to the real stories. They are never a source of truth.
5. **Stories are tests.** {#stories-are-tests} Stories double as interaction tests, accessibility checks and visual regression baselines. Component-level checks run in the medium tier; the Storybook build and its a11y checks run at the gate (§the-gate). Accessibility (keyboard, focus, contrast, roles) is part of the component contract. A new visual is also looked at once, rendered (a screenshot or by eye), before it is called done: a story can pass while the picture is wrong (an axis sorted alphabetically, a misplaced caret).
6. **Storybook is also the documentation hub, for non-UI modules too**: {#documentation-hub} architecture overviews, module and port docs, command catalogs (§command-reachable), state vocabularies (§declarative-representations), conformance status (§conformance-suites), the design system guidelines, and a rendering of these rules (their source stays the rule files, §rules-are-source).
7. **Docs are rendered from the source of truth, not copied.** {#rendered-docs} Pages embed or generate from `_spec/`, `.design/`, module READMEs and the registries (commands, error codes, concepts), so there is one place to edit and nothing to drift (§recursive-loop). Hand-written pages are for narrative that has no other home.
8. **Performance still applies.** {#ui-performance} Components obey §responsive-ui and §performance; stories include large-data cases to exercise them (guard tier where it matters).
9. **One icon set, one format.** {#one-icon-set} Icons come from one open icon set, the project's choice (Lucide is the example the patterns use: 24×24 grid, 2px stroke, round caps and joins, no fills, `currentColor`); an icon the set lacks is drawn in its format and guidelines so it is indistinguishable from the set. Icons are data (the set's node form, e.g. a list of SVG elements with attributes) in one registry in the common layer, rendered by one `Icon` component sized and colored by tokens; product code names icons, never pastes SVG. A gate check rejects custom icons that break the format.

## Views are representations {#views}

What a person is looking at is data, so it can be saved, shared, moved to another device and reproduced.

1. **A view is a representation**: {#view-is-representation} a query (what), a layout intent (how it should be arranged), and view state (pan and zoom, scroll, expansion, pins, selection). It lives in the representation layer (§declarative-representations) like any other state, not in a component.
2. **Surfaces are executors.** {#surfaces-are-executors} Desktop, phone, a wall display, XR, voice and an API each render the same view object natively (§executors-by-composition). Handing a view to another device or person hands over the object, and the receiving surface continues where the other left off.
3. **Views are reproducible.** {#reproducible-views} Opening the same view object gives the same picture of the same data (the query pins a snapshot when it must), and every element can be drilled down to the data it was derived from; views are never the source of truth.
4. **Large data loads by level of detail.** {#level-of-detail} Zooming in loads detail; zooming out shows summaries kept as derivations, cached by value hash (keyed by the source's hash and the parameters, so the same key gives the same result). Loading is paged and bounded like any read (each read has a stated cap on round trips, independent of history length).
5. **Views can be generated.** {#generated-views} A view may be built on demand from a question (an agent writes the query and the layout intent); the result is the same kind of object as a hand-made view and can be edited, saved and shared.
6. **Views are steered by commands, including by agents acting for the viewer.** {#command-steered-views} Navigation (open a document at a locator, select, reveal, open a panel) is a set of view commands over the view's state, used by the UI's own controls and by agents alike (§one-path-to-behavior). An agent changes only the view of the person who directed it (§requester-authority): a requested change applies directly, and one the agent decides on itself follows that person's consent mode (apply, propose, off; the one setting model of §one-consent-model). View state is live but not committed (§live-uncommitted-sharing) and is never part of history.
7. **Model and view state are reconstructible from data.** {#reconstructible-state} Everything a screen shows is derived from representations (documents, the view object, the session) and recorded transient state, never from history the UI alone held; so the state at any moment, such as where an agent's run left the app, can be rebuilt headless (§headless-mode) and rendered again: an eval viewer, a bug report, a handed-over screen.
