# Representations rules {#representations-rules}

State as data: declarative, recursive, streamable; committed vs transient; stable addresses and collaboration; transactions and optimistic state.

## In brief

**State as data** (§declarative-representations). One declarative, recursive tree form (spelled however the project chooses: S-expressions, JSON, ...), streamable, round-trippable, versioned
with migrations. Executors (renderers, runtimes) are bound by composition and never become the source of truth. Derived
data stays out. Each representation is its own module. Strict parsing everywhere; only agent and user inputs are
parsed leniently, repairing mechanical slips and reporting them. Every parameter that sizes work has a maximum, refused
before allocating (§bounded-work).

**Committed vs transient** (§committed-vs-transient). Transient state (drag, draft, preview) is an overlay ending in one commit or a cancel,
never a mutation; use the narrowest place: view-local → model overlay → committed. A pending optimistic change is a
transaction, not transient state. Bulk data is not tree nodes.

**Identity and collaboration** (§identity-and-hashing). Stable addresses (paths of sibling-unique ids; a document may make ids document-unique); operations address by id, rebase through moves, are versioned and idempotent. Merkle subtree
hashes (`hashNode`) for sync; value hashes for equality and caches. Collaboration strategies (server-ordered log, CRDT,
branch and merge, leases) are adapters behind one sync port; their types never leak past the adapter.

**Transactions** (§optimistic-transactions). A transaction is data, all-or-nothing, one round trip. Optimism lives in the one shared replica
(`effective = confirmed ⊕ pending ⊕ drafts`), never in a component. Client-generated ids, idempotent submission (ids are per
actor: outcomes keyed by (actor, id) with a content hash), rebase (never blind reapply), status visible as state, rejected
changes (also local refusals) rescued as data to a branch or copy. Effects outside the documents are outbox entries
performed after commit, never inside a transaction. Batches span documents and ports; writes are buffered to save boundaries; validators run on every commit and merge, and an operation they refuse changes nothing.

Bootstrap patterns: §representations, §committed-transient-identity, §transactions.

## Representations are declarative, recursive and streamable {#declarative-representations}

All application state has a declarative representation: plain data that fully describes it, with no behavior attached. → [§representations](bootstrap-patterns/representations/README.md)

1. **Declarative only.** {#declarative-only} The state layer holds *descriptions* (what), never executors (how). Handles, sockets, GPU buffers, workers, timers and closures live in runtimes, not in state.
2. **One recursive form.** {#one-recursive-form} State is a tree of nodes built from a few primitives (atoms and tagged lists). The spelling is the project's choice and a detail: S-expressions are one (small, human- and agent-readable, diffable, trivially recursive; the examples in these rules and patterns use them), JSON another. Whichever the project picks as its text spelling, the others (JSON, binary) are encodings of the same tree. Atoms are lossless: strings, float64 numbers (including `-0`, NaN, infinities), `bigint`, booleans and null; exact decimals are tagged forms such as `(decimal "12.50")`. Every encoding round-trips every atom kind.
3. **Streamable at every level.** {#streamable} Any state can be sent as a stream, composing with the streaming surface (§api-boundaries):
   - *Snapshot + operations*: an initial tree followed by a stream of operations (§ops-address-by-id), so a consumer rebuilds and tracks state incrementally.
   - *Incremental text*: printing and parsing work on chunks, so a large or still-growing state can be consumed before it is complete.
   - *Subtrees*: any part of the state can be addressed (by its entity address, §stable-entity-ids) and subscribed to on its own.
4. **Round-trip and equality are guaranteed.** {#round-trip-equality} `parse(print(x))` equals `x`; applying the diff of `a` and `b` to `a` gives `b`. These are tested properties (quick tier, ideally property-based).
5. **Executors are bound by composition.** {#executors-by-composition} A *runtime/executor* interprets a declarative description (render a board, run a simulation, perform an effect). Executors implement ports (§interface-boundaries) and are attached to state in the composition root, never from inside the state layer, so the same state can be run by different executors (a GPU renderer, a worker, the main thread, a remote service, a test double) or just inspected.
6. **Commands operate on representations.** {#commands-on-representations} Commands (§command-reachable) take and return representations, and mutating commands are expressed as operations (§ops-address-by-id). Command logs, undo/redo, replay, persistence and agent inspection fall out of this.
7. **Derived data stays out of the representation.** {#derived-data-outside} It is computed from it (queries and derivations) and cached per immutable snapshot. What is committed and what is transient: §committed-vs-transient.
8. **Versioned.** {#versioned-representations} Vocabularies evolve by explicit migrations (pure `Node → Node` functions). Stored documents are migrated on read or by an explicit batch migration, never left in mixed versions silently; derived caches are keyed by version and simply miss. The spec records the vocabulary (§spec-folders).
9. **Representations are their own (sub)modules.** {#representation-modules} The tree, printer/parser (the only place the syntax is defined), operations and streaming live in a common `repr-core`. Each domain representation (a document, a whiteboard, UI state, a DB schema, ...) is a separate module that depends only on `repr-core` and the common base (`lib/core`), never on executors, UI libraries or providers. A domain module owns its **vocabulary**, validation, **migrations**, accessors, encodings, conformance suites (§conformance-suites) and **query functions**. Small representations may start as a submodule of the owning product module and are promoted on reuse (§promote-on-reuse).
10. **The parser repairs trivial slips at agent-facing boundaries.** {#parser-repairs-slips} Agents and humans write representations and queries by hand. A *lenient* mode repairs only mechanical slips (unbalanced closing at the end, code fences, smart quotes and similar); it is deterministic, **never guesses meaning**, and **always reports** what it changed alongside the normalized text. Strict parsing is the default everywhere (persistence, wire, storage, inter-module); lenient parsing is only for command and query inputs from agents and users (§command-reachable), and destructive commands may require strict input by policy (§least-privilege). → [§representations](bootstrap-patterns/representations/typescript.md#lenient-parsing-and-trivial-repairs)
11. **Work a representation sizes is bounded before it starts.** {#bounded-work} Every parameter that sizes work or memory (a count, a repeat, a depth, a resolution, a range of copies) has a maximum in its language's schema, and whatever acts on it (a compiler, a resolver, an engine, a query) refuses a value past it with a coded error before allocating. A larger bound is a deliberate change with its reason. Why: representations arrive from URLs, files and agents, and one unbounded number can hang a process or exhaust memory before any limit or signal is checked.

## Committed vs transient state {#committed-vs-transient}

What the document is, what is in flight, and how interaction becomes change. → [§committed-transient-identity](bootstrap-patterns/committed-transient-identity/README.md)

1. **Committed state** {#committed-state} is the document: the declarative tree (§declarative-representations) that is persisted, shared, undoable, replayable and merged. It changes only by committed operations (commands, §command-reachable), each atomic and consistent.
2. **Transient state** {#transient-state} is everything in flight: a drag, a brush stroke being painted, a preview, a draft form. It does not enter history, persistence or collaboration until committed. An optimistic change awaiting confirmation is not transient view state: it is a *pending* transaction in the shared store (§optimism-in-store), visible everywhere and confirmed or rejected as a unit.
3. **Transient state is an overlay, not a mutation.** {#transient-overlay} An interaction opens a *draft* on the document: it updates the overlay at interactive rates (coalesced), executors render `effective = committed ⊕ overlay` immediately, and the interaction ends with exactly one **commit** (one operation, one undo step) or a **cancel** (overlay discarded, committed state untouched).
4. **Three places state can live** {#three-state-places} (pick the narrowest that works): view-local (hover, focus, open/closed; nobody else needs it, §thin-view-layer) → model-level transient overlay (representable, visible to executors and agents, not committed) → committed document. This item is the one place this is defined; others point here.
5. **Live-but-not-committed sharing** {#live-uncommitted-sharing} (cursors, selections, a stroke being drawn by a peer) uses a separate ephemeral *presence* channel with last-write-wins semantics; it never mixes with the committed log.
6. **Executors never become the source of truth.** {#executors-not-truth} Interaction in the world (drawing on a whiteboard, dragging a shape) produces *intents*; intents become draft updates and then commands, which change state; state is reconciled back to executors. Reconciliation is a pure, idempotent function of the effective state, skips unchanged subtrees by hash (§merkle-hashing), and uses operation origins (§idempotent-ops) to avoid echo loops.
7. **Bulk data is not tree nodes.** {#bulk-data-not-nodes} High-volume payloads (stroke samples, images, audio) are referenced data (stored outside the tree and pointed at by reference), not lists of number atoms.

## Stable identity, hashing and collaboration {#identity-and-hashing}

What makes representations safe to edit concurrently, sync and cache. → [§committed-transient-identity](bootstrap-patterns/committed-transient-identity/README.md)

1. **Entities have stable addresses.** {#stable-entity-ids} Any node that is an entity (something users or other nodes refer to, that can move or be edited concurrently) carries an `id` assigned at creation, unique among its siblings and never reused there. Its **address** is the path of ids from the root: `/cytoplasm/nucleus/p1`, and `/cytoplasm/*` names a subtree. An address names, it doesn't count: a path of indices is a position, a path of ids is identity, so inserts and reorders never change an address. A move does: it is an operation like any other, and whatever the document's history reaches that named the old address (operations, links, attachments) follows it to the new one; a reference it can't reach (another document, an outside link) goes stale visibly, naming the move, never silently resolving to whatever has that address now. A document type may make its ids unique across the whole document; then the id alone is a complete address and survives moves. Leaf values and structural nodes need no id.
2. **Operations address by id, never by position.** {#ops-address-by-id} `set-attr`, `insert` (parent + after-sibling), `remove`, `move` target addresses, so they survive concurrent inserts and reorders and many commute; an operation made against an address that a concurrent move changed is rebased through the move, never applied to whatever sits there now. Keyed children also make diffing and reconciliation exact (moves are moves, not delete+insert). Positional patches are only for trees without entities.
3. **Subtree hashing (Merkle).** {#merkle-hashing} Nodes have a content hash over a *canonical* encoding (tag, atoms, child hashes), cached on the immutable node, so unchanged subtrees keep both their reference and their hash. Hashes give O(1) equality, cheap change detection, cache keys (query and derivation caches), content-addressed storage, and efficient sync (compare roots, descend only into differing subtrees). Identity (id) and version (hash) are different things.
   **Two hashes, two jobs.** The *structural hash* (`hashNode`) covers the tree exactly as written; sync, op base/result checks, storage integrity and mirrors use it, because peers must agree on bytes. The *value hash* (`valueHash`) first maps every subtree to its canonical spelling (a table written row-wise to its column-wise layout; anything else a vocabulary declares equivalent) and then hashes structurally; value equality, derivation and query cache keys and content-addressed dedup use it. When a vocabulary declares no equivalent spellings the two are equal. Never mix them: a cache keyed by value hash may serve a document whose structural hash differs, and that is the point.
4. **Operations are versioned and idempotent**: {#idempotent-ops} each carries an operation id, the base hash it was made against, its origin (`ui`, `agent`, `executor:<name>`, `remote:<peer>`) and optionally the result hash. Re-applying an operation is a no-op; a base mismatch triggers a rebase or a coded error (§stable-error-codes); result hashes verify convergence.
5. **Collaboration strategies are a library of adapters, chosen per document type.** {#collaboration-adapters} No single strategy fits everything, so the library offers several behind one sync port (§compose-through-ports), all presenting the same document API (committed, effective, drafts; §committed-vs-transient) and the same ids, operations, hashing and origins: a **server-ordered log** with optimistic apply and rebase (the default for structured documents), a **CRDT** (concurrent editing of the same text or sequence, offline-first), **branch and merge** (long-lived divergence with reviewed merges), and **exclusive leases** (one writer at a time, e.g. a generated artifact). Each adapter declares its properties: offline support, how conflicts are handled (auto-resolved, surfaced as data, prevented), intention preservation, history. An application picks per document type and may mix them; conflicts that a strategy cannot resolve on its own go through a merge defined per language (one that yields conflicts as data). A strategy's library types never leak past its adapter: storage, wire and agents see the document API, not the CRDT's or the log's internals.

## Transactions and app-wide optimistic state {#optimistic-transactions}

Changes travel as transactions: one unit of atomicity, of round trip, of optimism and of undo, used by the UI, commands, agents, remote commits and background workers alike. A small common library owns them. → [§transactions](bootstrap-patterns/transactions/README.md)

1. **A transaction is data.** {#transaction-is-data} It is a form in a small language: steps that are commands or operations (§command-reachable, §ops-address-by-id), names binding a step's result for later steps, preconditions (expected hashes or versions, checked like a conditional write), and a label. It can be printed, logged, sent, dry-run and replayed like any representation.
2. **All or nothing, in one round trip.** {#all-or-nothing} A transaction executes atomically against the store that owns its documents; a remote store executes the whole transaction server-side in one call. A transaction never waits on the outside world, and nothing outside the documents happens inside one: an effect on the world (mail, a provider call) is an outbox entry the transaction writes, performed after commit by a worker, so a preview, a replica's local run or a refused transaction never sends anything. Long-running work runs as steps that each submit transactions (a durable workflow, if the project has them).
3. **Optimism is a layer of the shared store, never of a component.** {#optimism-in-store} Every replica (a tab, a worker, a server mirror) keeps `confirmed` state plus an ordered queue of `pending` transactions, and the state everything reads is `effective = confirmed ⊕ pending ⊕ drafts` (§transient-overlay). Every model and view derives from `effective`, so an added shape appears at once on the canvas, in the frame's outline, in the board's shape count and in what an agent reads, and disappears from all of them together if it fails.
4. **One code path.** {#one-code-path} The optimistic change is the transaction that is sent. There is no separate local mutation and no hand-written rollback: a rejected transaction leaves the pending queue and `effective` is recomputed.
5. **Client-generated ids, idempotent submission.** {#client-ids} New entities and transactions get their ids on the client, so a server acknowledgment matches by id and nothing is re-keyed or duplicated. Transaction ids are per actor: the server records each outcome by (actor, id) with a hash of the content, so resending an id whose outcome is unknown (a dropped connection) with the same content returns the original outcome instead of applying it twice, the same actor reusing an id for other content is a conflict, and another actor's equal id never collides (ids are guessable; one actor's ids must not block or reveal another's). Only a rejected transaction is retried under a new id.
6. **Rebase, never reapply blindly.** {#rebase} When confirmed state moves (a remote change, an acknowledgment), pending transactions are re-applied on top of the new confirmed state in order; one whose preconditions no longer hold is rejected with a coded error (§stable-error-codes) and reported, not silently dropped.
7. **Transaction status is visible state.** {#visible-tx-status} Each transaction is pending, confirmed or failed (with its code), observable and queryable; a failed send shows in the UI as data with retry and discard, not as a toast that vanishes. A rejected change that the author may still want is kept, not discarded: it is **rescued** into a branch or a copy the author can review and merge later, so nothing typed is lost to a conflict. A rescued change is kept as data (the state it was made on, that state with the change, the operations) that can become a branch, and it covers a change refused locally because a concurrent one already arrived, not only one the server refused.
8. **One owner of the queue per replica.** {#one-queue-owner} A replica's pending queue lives with its store: in a shared worker that tabs view, or per tab with other tabs treated as remote peers. Components never keep queues of their own.
9. **Transactions span documents.** {#cross-document-transactions} A shape added to a frame plus the board's shape count plus a collaborator's notification is one transaction, confirmed or rejected together.
10. **A batch spans ports.** {#cross-port-batches} Writes are data, so a transaction may carry steps for several ports at once (documents, log appends, telemetry, job-queue enqueues, command-layer state) when one store or one server-side runtime owns them. Starting a job (its documents, a log entry, a telemetry trace, its first queued work item) is one transaction and one round trip, executed by the runtime on the server; ports expose their writes as transaction steps rather than as calls that each go to the store.
11. **Writes are buffered to save boundaries.** {#buffered-writes} Inside a loop (a turn, a slice, a gesture), writes accumulate in a unit of work and are flushed as one transaction at declared **save boundaries**; reads inside the loop see the buffer (read your writes). Where the boundaries are is a decision about crash loss: anything an external effect depends on is saved before the effect runs, and everything since the last boundary must be safe to redo under the same idempotency keys.
12. **Validators run on every commit and merge.** {#validators} Each language or application registers checks that run on a transaction's result before it commits and on a merge's result before it lands: invariants that must keep holding, rules on which states may follow which. A failure is a coded error and nothing commits. The base runs the validators; what they check (link integrity, declared per kind of link, is the built-in one) belongs to whoever registers them. Every operation that patches the state is checked by a conformance case run over the app's composition: given a patch the validators refuse, the operation returns a coded refusal, the state's hash is unchanged and no history step is recorded; only issues the patch introduces refuse, issues already present do not. Why: an operation that skips the validators lands a state its own language refuses and reports success.
