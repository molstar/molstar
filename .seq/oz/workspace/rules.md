# Workspace rules {#workspace-rules}

Which tools the repository runs on and how packages are named: one entry point, language-neutral contracts, family
folders and one linter and formatter. The top-level layout is the layout module
([../layout/tree.md](../layout/tree.md)); how work is run is [../_core/workflow.md](../_core/workflow.md).

## In brief

The workspace is multi-language by construction: languages meet only through language-neutral contracts
(representations and encodings, the wire protocol, command schemas, error catalogs, fixtures), and a module gets
per-language subfolders only with a second implementation. One tool (the examples use mise) pins toolchains and defines the tasks everyone runs: repo-wide ones at the root, a
folder's own in that folder; several processes together are one parallel task. Family folders, flat package names
(`lib/core/errors` → `@scope/core-errors`); imports always use the package name, never a relative path across packages.
One linter and formatter for code (Biome, say), a narrow fallback for the rest (Prettier, say), one line width; import
direction is a lint rule. Existing code
adopts new rules through ratchets: a checked-in baseline per file and rule that only shrinks.

## Workspace and tools {#workspace-and-tools}

1. **A multi-language workspace with one entry point.** {#one-entry-point} The workspace is language-neutral even while it has one language: modules are organized by what they do, not by language; each package uses its language's own manifest (`package.json`, `pyproject.toml`, `Cargo.toml`), with the per-language workspace files at the root. **One entry-point tool** (mise in the examples) pins every toolchain version and defines the tasks (`setup`, `test`, `gate`, `nightly`, ...), so people, agents and CI run the same commands (§ci-enforces). The root config holds only the repo-wide tasks; a folder's own tasks (a prototype, an app, a service, a tool) live in that folder's config and run by folder (with mise, `//<folder>:<task>`), so the root file stays small and one command lists everything. Running several processes together (a service and the app that talks to it) is a task too, run in parallel by the same tool, not a separate process manager. A module gets per-language subfolders only when it gains a second implementation.
2. **Languages meet only through language-neutral contracts**: {#language-neutral-contracts} representations and their encodings (§declarative-representations, and their encodings and storage formats), the wire protocol (one framed protocol for every stream, independent of transport), command schemas (§data-described-commands), error catalogs (§cataloged-codes) and conformance cases stored as data (§cross-language-cases). No cross-language FFI-shaped coupling of internals; a second implementation of a module in another language is done when it passes the same fixtures.
3. **Related packages share a family folder; package names stay flat.** {#family-folders} A group of packages with a common prefix lives under one folder named for the prefix (`lib/repr/core`, `lib/repr/board`, `packages/product-x/models`), and each package is named by joining the path below the top-level folder with `-`, under the workspace scope (`@scope/repr-core`, `@scope/repr-board`, `@scope/product-x-models`). A family folder is never a package itself. Imports always use the package name, never a relative path across packages, so moving a package between folders changes no import. The same holds in `apps/` and `services/` (`apps/product-x/web`, `services/product-x/api`), where each leaf folder is one deployable.
4. **One linter and formatter, with a narrow fallback.** {#one-linter-formatter} One tool lints and formats everything it supports (with Biome: TypeScript/JavaScript, JSON, CSS); a fallback formats only what it cannot (with Prettier: Markdown, MDX, YAML), and no file is covered by both. One line width everywhere (120 in the examples). Editors, agents and CI use the same configs: the `format` task writes, the `lint` task checks and is part of the gate (§the-gate). Rules are enforced mechanically wherever a tool can express them: provider SDK imports only in their runtime packages (§provider-runtime-packages), no `process.env` outside composition roots (§one-composition-root), no undeclared dependencies, and the dependency direction (§common-vs-product): in imports by per-folder lint rules, so it shows while editing, and in the package manifests by a gate script. A rule a tool can check is a lint rule or a gate check, not a review comment. Existing code adopts this through **ratchets**: a baseline of current findings per file and per rule, checked in; the gate fails on any new finding and the baseline only shrinks.
