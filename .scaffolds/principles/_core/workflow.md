# Workflow rules {#workflow-rules}

Agent context and specs, design/plan/implement, iteration, and keeping design, spec and code honest.

## In brief

One line per section; read the section before acting on it.

- **Context** (§agent-context): the principles are the source; `AGENTS.md` binds code to them, `_spec/` mirrors the
  code; load only your slice; agent context is never auto-formatted; nothing committed names a local path.
- **Design first** (§design-plan-implement): research precedents, surface tensions to the author, run the self-check
  on the design's own claim, agree it in `.design/<area>/<topic>.md`; then a short plan, a checklist, a loop and
  `state.md` (the current state only) in `.execution/<work-id>/`, committed with the work and never cited from outside.
- **Close a piece of work** (§reconcile-before-merge): fold what it taught into designs, spec and issues; ask the
  fold-back question (a `foldback.md` when the answer is yes, merged only on the author's decision); then close the
  work folder: it stays as the work's archive, never edited.
- **Records** (§permanent-record): a record in `.records/<work-id>/` at every sitting, compaction or handoff, never
  edited after; the record is cited, the archive beside it is not.
- **Agents at work** (§agents-at-work): commit at each small green step, by path; green is an exit code with tests
  run; reuse the agent that holds the context; a permission refusal goes to the author.
- **Lanes** (§lanes, in [lanes.md](lanes.md), read only when fanning out): one writing lane per worktree, a brief that names
  model, effort and every check; lanes don't loosen checks, write the work folder
  or stage the lockfile; the orchestrator merges one lane at a time and gates between.
- **Iteration** (§iteration): prototype often, outside the main code, each under its own scope; the author uses it before it ends, and it ends with residuals; a finished prototype is frozen.
- **Drift** (§recursive-loop): disagreement is information; triage it, write a drift note, never bend either side
  silently; design changes are the author's call (§upward-authority).
- **Agreement** (§gaps-queue, §shared-ownership): building must not outrun agreement; the three gap lists are asked at
  every gate; contributors own what they touch, and agreement is emergent.
- **Proof** (§upward-authority, §green-is-exit-code): a report, yours or an agent's, is not proof; re-run its checks.
- **The author** (§author): start from their words, reconcile rather than correct, ask only at real choice points
  with a recommendation; only the author's words close a decision, and one accepted as recommended keeps its
  alternatives (§authors-words-decide).

## Codebase structure and agent context {#agent-context}

1. **These modules are the source of the principles.** {#rules-are-source} Skills load them for agents; a project may render them as docs for people. Nothing else restates them.
2. **AGENTS.md** {#agents-md} files (multiple, nested) bind a specific codebase to the principles: module map, build/test scripts, local conventions.
3. **`_spec/` folders hold a semantic mirror of the code** {#spec-folders} (global at the repo root, local per module), so agents can query meaning without reading everything. The spec describes the code *as it is*; intent lives in `.design/` (§design-plan-implement). **Spec = map, code = territory**: when they disagree, that is a signal to triage (§recursive-loop), not a verdict. Registries (commands, error codes, concepts) are the machine-readable part of the spec; `_spec/` links to them instead of copying them. A spec line that refuses or restricts (an error code, "only", "never") states its reason, and a review asks for it on the lines a change adds: a restriction with no reason is the one nobody questions. → [§spec-mirror](patterns/spec-mirror.md)
4. **Context is a budget.** {#context-budget} AGENTS.md files and spec entries stay short. An agent loads the slice it needs: the principles README, the modules for its area, the module's AGENTS.md and `_spec/`, and the relevant registries.
5. **Agent context is never auto-formatted.** {#no-auto-format} `.principles/`, the instance folder (`.<instance>/`: its skill, manifest, modules and designs), `.design/`, `.sources/`, `_spec/`, `.execution/`, `.records/`, skills (`.agents/`), `AGENTS.md` files, and any other folder a project keeps plans, progress notes or session records in, are excluded from every formatter and linter. The one exception is the package's checks, `.principles/_checks/*.ts`: they are code, linted and type-checked as code. Agents load and edit these files; a tool that rewraps or reorders them produces diffs nobody wrote, makes what an agent already read stale, and churns reviews. Whoever writes them keeps them tidy.
6. **The codebase is machine-invariant.** {#machine-invariant} Nothing committed names a path on one person's machine: no home or temp folder, no drive path, in code, docs, principles or skills alike. References point inside the repository by relative path, at a published location (a repository URL), or name the thing in words; material from elsewhere that a document relies on (a screenshot, a reference) is copied into the repository beside it, sized for review. This holds for the work folder too (`.execution/`, committed and kept, §permanent-record): a lane's worktree is named by its relative place or its branch, a scratch folder in words. Local scratch files that tools and tests write (databases, run outputs, eval results) go in a gitignored `.tmp/` at the repository root, never beside the sources or at the root itself, and committed files never refer to what is in it. The path check (`_checks/paths-check.ts`) enforces this in the gate.

## Design, plan, implement {#design-plan-implement}

Three kinds of files, with different lifetimes (→ [§workflow-files](patterns/workflow-files.md)):

| Folder | Holds | Lifetime | Tracked |
|---|---|---|---|
| `.design/` (global, root) | what we intend and why: decisions, rejected alternatives, invariants; a folder per area, one file per topic (`.design/<area>/<topic>.md`); designs of prototypes in `.design/_prototypes/<name>/` | durable | yes |
| `_spec/` (global + local) | what the code is (§spec-folders) | durable | yes |
| `.execution/<work-id>/` | plan, checklist, loop, state, findings, drafts, briefs, drift notes, followups: the working memory of one piece of work, and after its close the archive of how it went | edited while the work runs; after the close kept, never edited | yes, never cited (§execution-unreferenced) |
| `.records/<work-id>/` | one record per execution session: asked, decided, delivered, learned, left open (§permanent-record) | permanent | yes |

1. **Design before implementing** {#design-first} for most functionality (trivial changes exempt). The agreed design is a short file in `.design/<area>/<topic>.md`; being there means agreed (no status field), except a marked provisional section (§gaps-queue); drafts live in the work folder. A prototype's designs live in `.design/_prototypes/<name>/` and record what it explored (§iteration). Before it is agreed, a design runs the four-step check on its own claim (§self-check, "On a design") and keeps the result as a short section; a design for a new visible part or gesture is agreed with an interactive mock and a named precedent, and one that adds something drawn with its defaults (the ui module, if used). It is kept current by editing in place (git keeps the history), and updated or deleted when it stops being true.
2. **Look for precedents before designing.** {#precedents} A design starts from research sized to the decision: how this was solved before in this codebase (designs, records, residuals, code), in the sources (§sources), and outside (libraries, projects, papers, standards). It names what it builds on or departs from, with links and a line each on what was taken and what was not, or says there is none; for anything a person uses, that includes what users can do in comparable tools, each listed as built, planned or refused, with the reason. Research notes stay in the work folder; external material worth keeping becomes a source (`.sources/<name>/`).
3. **Surface tensions to the author; don't resolve them silently.** {#surface-tensions} A tension is any place where two things the design must respect pull apart: the author's words and a principle (§reconcile-dont-correct), two principles, a precedent and this codebase, the design and existing code, or a cost against a benefit. Each one is written down explicitly, with the options and a recommendation, and brought to the author at the point it matters (§reduce-load), not buried in a decision. A tension that clarification doesn't dissolve is worked through the four-step check (§self-check). The design records how each was settled, and one still open stays visible as undecided (§four-outcomes) rather than built over.
4. **A short plan, and a checklist beside it.** {#plan-and-checklist} Once the design is agreed, `plan.md` says what and why: stages and their order, the testing strategy (see the testing module, if used), risks, what is out of scope, and each lane's model. It is written once, about a page or two; a re-plan adds a dated line rather than rewriting it, and it holds no status. `checklist.md` beside it has one line per item, the review, integration and merge gates included, each ticked with its commit as it lands; it is what the loop and the finalize check read. Why: a plan that also carries status, decisions and history grows past what anyone rereads, and the ticks get lost in it.
5. {#loop-file} Once the plan is agreed: write a **loop file** (`.execution/<work-id>/loop.md`) that governs implementation. The loop uses the testing strategy to decide what to run when (targeted, then the gate).
6. **The loop maintains `state.md`, the current state only**: {#state-file} where the work stands now (in progress, next, blockers, how to verify), rewritten in place at every meaningful step and before stopping, so another agent can pick it up cold (budget or token exhaustion, a crash, a handoff); about a screen. It is not a log: decisions go into their design (and the record says how they were made), findings into `findings.md`, what happened into git and the record. The loop's first instruction is to read `state.md`; the fold-back check notes one past 600 words. Why: a state file that accumulates history stops saying where the work is.
7. **`.execution/` is never referenced from outside itself.** {#execution-unreferenced} No code, spec, design, test, comment, commit message, record or doc may link to or depend on a plan, loop, state, draft or brief. Anything worth keeping must live in a durable place: what is true in the design, the spec or the code, how it went in the record. The folder is committed and kept (§permanent-record), but as evidence, not as a source: it is found by its work id (the name its record folder shares), never by a link, so nothing that is read as true can rest on a plan that was never agreed. Files inside the folder may refer to each other.
8. **Reconcile, then close.** {#reconcile-before-merge} Before the work is called done, its folder is reconciled: decisions into `.design/` (§design-in-place), what the code now is into `_spec/` and the code, drift notes resolved or turned into followups (§followups). Then the **fold-back question**: did the work teach anything about how work is run or how code is shaped? The record's Learned section answers on its own line, `Fold-back: none` or `Fold-back: proposed (foldback.md)`. A `foldback.md` holds the proposals with their evidence, the earlier fold-backs' rules re-checked (held, amended, dropped) and the self-check (§self-check), and is applied only after the author's decision line: merged, merged in part, or not merged (an exploration or a spike is not merged, and its lessons stay in its archive). Then the folder closes: `state.md` ends with `Closed <date>: <record file>`, and nothing in it is edited after. The finalize and fold-back checks enforce this; the steps: [FINALIZE](patterns/workflow-files.md#loopmd) and [foldback.md](patterns/workflow-files.md#foldbackmd-when-the-work-taught-something). Why: asked at every close, learning is continuous without a document per close.
9. **Followups.** {#followups} Work discovered but out of scope is never left as a TODO in code or buried in a plan. Each becomes an issue in the tracker (or wherever the project's manifest says its open items go), stating the context, why it was deferred and what done looks like (rough design thinking goes in the issue, not in `.design/`). Small cleanups go in the current work instead if cheaper than recording them. In a prototype, followups are its residuals instead (§residuals).
10. **Handoff across machines/worktrees.** {#handoff} The work folder travels with the work branch: commit it (the orchestrator does, §lanes-report-not-write) and push, and the receiving agent starts from `state.md`. Uncommitted state is lost at a handoff, so `state.md` is committed before stopping.
11. **Every session leaves a permanent record; the work folder is kept beside it.** {#permanent-record} Each sitting, compaction or handoff writes a short record in `.records/<work-id>/<date>-<name>.md`: what was asked, decided, delivered and how it was verified, learned, and left open. Decisions are also copied into their design: the design says what is true now, the record how we got there. Records are never edited; code may cite a design or a record, never a plan. The closed work folder is the archive behind the record: complete, never cited, and kept as evidence for a later fold-back (the alternatives a draft weighed, each lane's findings). It holds what the process wrote (text, small one-off scripts); generated output stays in `.tmp/` (§machine-invariant), and a screenshot the record relies on is copied beside the record. The template: [§workflow-files](patterns/workflow-files.md#session-record-recordswork-iddate-namemd).
12. **Vocabularies are written down before they are built on, then kept stable.** {#stable-vocabularies} A **code vocabulary** (node kinds, a small language, an API) is what code, stored data and agents speak; a **product vocabulary** is what people read and say. Each is designed and reviewed on its own, with the mapping between them written down (which code term each product word shows, where one shows several or none): a code term never reaches a screen because it exists, and a product word never renames code. Each is written (terms, a sample, what it leaves out) before anything builds on it, a code vocabulary once it works headless and a product one before the screens that speak it: a short list in a prototype, reviewed by the author at a gate in the main codebase. After that either changes only as a design change, a code vocabulary by a migration or a deprecation, never a quiet rename. Why: a late change to one is a migration everywhere; to the other, a cost to everyone who learned it (§authors-words, §name-the-roots).

## Agents at work {#agents-at-work}

What every agent needs, alone or in a lane.

1. **Commit at each small green step.** {#small-green-commits} An agent commits whenever it reaches a small green step (it builds, a test passes, a check works), staging only its own files, by path, never everything at once (`commit -a`, `add .`). Why: nothing is lost, the history shows how the work went, and nobody's stray file rides in another's commit.
2. **Green is an exit code.** {#green-is-exit-code} A step is green when its checks exit zero, each run as its own command whose status gates the commit, with a non-zero number of tests run and no new skip or focus marks; never when a filtered view of the output looks right (a search for a summary line succeeds whatever the tests did). Why: a pipeline's status is its last command's, so a commit chained after one lands on a failure, and a filter that matches nothing exits zero too.
3. **Reuse agents that already hold the context.** {#reuse-agents} A follow-up on a subagent's work (a fix after its review, its next step, a question about what it found) goes back to that subagent, which still holds the files and reasoning. Start a fresh one only for independent work, when fresh eyes are the point (a review not anchored on the author's view, §upward-authority), or when the old context is exhausted or misleading. The loop file records which agent owns which task and roughly how much context it holds, so it can be continued, or replaced before its context is too large to be reliable.
4. **A refusal by the permission system is the author's call.** {#refusals-to-author} An agent whose action the permission system refuses (an edit to configuration, a lint or architecture rule, credentials) stops that step and reports the action and its reason; whoever it reports to brings it to the author with a recommendation and never performs it on its behalf, and no other agent's message counts as the author's approval (§upward-authority). Why: a refusal marks where a person decides; doing it one level up launders it.

## Iteration {#iteration}

1. {#prototype-often} Prototype often; do not fear rewrites.
2. {#prototype-outside} Prototype **outside** the main codebase, then port the validated design in. This does not conflict with §design-plan-implement: the prototype is how the design gets validated, and its output feeds the design. Prototypes live in `prototypes/<name>/` at the root, outside the build; for UI, a reference package (`prototypes/<design>-reference/`) shown in the project's component workbench (its reference section) is the prototype space.
3. **A prototype ends with residuals, not with everything resolved.** {#residuals} What it leaves for the next iteration (open drift, followups, known bugs, limits) is listed in its nested `_spec/residuals.md`, one line each, grouped and cited, instead of being filed as issues or fixed before it ends; what it taught goes into the principles and its designs (§reconcile-before-merge, §gaps-queue).
4. **Prototypes don't share a namespace, and a finished one is frozen.** {#frozen-prototypes} Each prototype names its packages under its own scope (`@scope-<prototype>/...`), so two prototypes never collide in one workspace and a new one reuses an earlier one's code by forking it, not by importing it; promotion into the main codebase renames the scope. Only work in flight is gated: once a prototype has ended (its residuals written), it is frozen, its tests leave the gate and run on demand, and it is kept only as far as it still builds. Nothing in flight depends on a frozen prototype.
5. **What people use is used by its author before it ends.** {#used-before-done} Tests and an agent's own checks come first, not instead: the author uses the work as its people would, on real data, with the agent standing by to fix what they find. In a prototype that is the last gate before the close; in work built in lanes it is continuous, each part used as it merges, with a look at what changed before the close. A novice pass may go before the author. Findings are counted by kind (a bug, a missing design, a look) as they come, and an observation a fix rests on states its conditions (a visible or hidden page, the browser, the pixel ratio) and is reproduced headless first, on a fake clock where time matters. What use finds is fixed, listed in the residuals, or folded back. How to run it: [use and the novice pass](patterns/workflow-files.md#use-and-the-novice-pass). Why: what matters in use passes every test written from the design, because the tests share the design's blind spots.

## Iterating on architecture, design and spec (the recursive loop) {#recursive-loop}

Principles, architecture, design, plan and code form a stack; `_spec/` describes the code layer. Each layer is a *hypothesis* about the layer below and a *constraint* on it. Truth about **what runs** is the code; truth about **what we intend** is the highest layer a human has agreed. When they disagree, neither side wins by default. → [§drift-triage](patterns/drift-triage.md)

1. **Disagreement is information.** {#disagreement-is-information} Never silently bend code to match a design, and never silently edit a design or spec to match code. Both skip the question of which one is wrong.
2. **Triage every drift into one of four outcomes:** {#four-outcomes}
   - **Code is wrong**: the design states intent we still hold. Fix the code.
   - **Spec is stale**: the code is right and the spec lagged. Update the spec in the same change.
   - **Design is wrong**: following it produces bad code (awkward, slow, leaky, repeated workarounds). Change the design, then the code. This goes through §design-plan-implement at the size it warrants.
   - **Undecided**: do not guess, and do not build further on the contested point; if it outlives the work, it becomes a followup issue (§followups).
3. **Bending signals.** {#bending-signals} Evidence that the design should bend, not the code: the same workaround appears 2-3 times; a port needs an escape hatch that exposes a provider; tests need mocks of internals instead of ports; an invariant is violated by every real caller; a plan step cannot be written without contradicting the design.
4. **Stop and write a drift note.** {#drift-notes} An agent that finds the design or architecture blocks a correct solution stops, writes a short note (what, evidence, proposed outcome) in `.execution/<work-id>/drift/` (a lane puts it in its report, §lanes-report-not-write), and continues on unaffected work; it lands no code that contradicts an agreed design until the note is resolved. The result is the fix (code, a spec entry, or the in-place design edit, §design-in-place); the resolved note is deleted, and one that outlives the work becomes a followup (§followups). A finding that repeats one already fixed is a class: its rule goes into the design or `_spec`, a sweep test covers every place it applies, and the open instances fold into that one item, briefed to a strong lane, never fixed one by one.
5. **Design changes go through the author.** {#upward-authority} Agents may fix code and update stale spec entries freely (outcomes 1, 2). Changing design, architecture, ports or principles (outcome 3) is the call of the author the agent works for: the agent brings the evidence and the migration plan, and the change lands when that author contributes it. There is no further sign-off (§shared-ownership).
   A subagent's or reviewer's report is not proof: the checks it claims are re-run before its conclusion is acted on. Nor does it close a decision: only the author's words do (§authors-words-decide).
6. **Recursive scope.** {#recursive-scope} The same loop applies at every level: code vs design, design vs architecture, architecture vs principles. A drift is resolved at the lowest level that can absorb it; if it cannot, escalate one level up. These rules change the same way: evidence from real work, then a human decision.
7. **Rewrites are the loop working.** {#rewrites} When repeated bends accumulate, re-derive the design from what the code taught us (§iteration), then replace the stale parts rather than patching around them.
8. **Update the design in place.** {#design-in-place} An outcome 3 change edits the affected `.design/` document directly, and the commit message carries the evidence and what was rejected. If the reason is non-obvious to future readers, add it under the design's "rejected alternatives". Git history explains how we got here; there is no separate log or notes folder.
9. **Drift is checked mechanically.** {#mechanical-drift-checks} The finalize step fails while a drift note is open. At the gate the merge check rejects references into the work folder, and the drift check fails on `_spec/` links and registry references (commands, error codes, concepts) that no longer resolve, and warns when a package's source changed while its `_spec/` did not (updated in the same change, or recorded as a followup). Every list or fact that describes code (an index page, a configuration table, a feature list's statuses, a version) is generated from, or tested against, the code, never kept by hand; a lane's feature row moves with its lane, as its own entry where the list is a hot file (§commit-often). Why: each lane keeps its own spec true, but lists copied by hand fall behind at the scale of a round.
10. **Building must not outrun agreement; the gaps are asked.** {#gaps-queue} With agents, building outruns agreement, and incoherence collects in three gaps: *built but not agreed* (open drift, deviations, provisional sections), *agreed but not built* (followups, plan items), *built but not adopted* (lessons not folded back). The orchestrator keeps each as a list, one line per item, grouped, and ends every gate's message to the author with what was raised since the last, each a yes or no with a recommendation; nothing reaches the close unasked. A lane does not build on a point waiting in the first gap; when that gap grows faster than it is decided, work slows to the author's pace. A lane that builds differently from a design writes it only in the design's marked "Spelled while building (<lane>, <date>; provisional, for the author)" section, until the author's words, dated, rewrite the marker (§authors-words-decide). A default stands as documented or is confirmed by use; only unsure ones that change what people see or do are asked. Why: a gap shown is not a gap asked.
11. **Contributors own what they touch; agreement is emergent.** {#shared-ownership} No module, pattern or design belongs to a person, and there is no sign-off role. `main` is what authors contribute: whoever changes something owns that change, keeps it consistent with the rules and designs around it, triages the drift it causes, and takes up the "To decide" items it touches; agreement emerges from what authors build on, change or revert. A source names where material came from, not who controls it. An agent works for an author, the person who asked, and brings what needs a person's decision to that author (§upward-authority).

## Meeting the author where they are {#author}

The person who brings an idea is the author of the application, not a client of the principles. Agents help them turn their ideas into a good application in their own terms, and use the principles as the means, not the subject.

1. **Start from the author's words.** {#authors-words} Capture the idea in the author's vocabulary and structure first (a doc, a sketch, a list of wishes), keep it as the reference, and translate it into the principles' terms second. A translation that loses something says what it lost.
2. **Reconcile, don't correct.** {#reconcile-dont-correct} Where the idea and the principles disagree, show both sides and the options: often the principles have a primitive the idea needs, sometimes the idea shows a gap in the principles (§recursive-loop), and sometimes it is a genuine choice the author makes. A reconciliation is a document of its own, kept beside the idea, not a rewrite of it.
3. **Keep a model of the author, labeled as one.** {#author-model} Agents keep an explicit, inspectable model of the author's intent: goals, decisions already made, preferences, recurring corrections, vocabulary. It is owned and correctable by the author, says where it is uncertain, and is used to propose, never to decide: when the model and the author disagree, the author wins and the model is updated.
4. **Separate what belongs to the application from what belongs to the base.** {#application-vs-base} Application semantics live with the application (`.sources/<name>/`, the [sources pattern](patterns/sources.md)); only what several applications need, or what one cannot build on top, becomes a base primitive. Each application tests the principles: its reconciliation lists what the base offers, lacks, and left to it on purpose. A design that composes an application from the base (views, navigation, optional analyses) says in its Intent that it is application-level work on the public surface, naming the base parts it uses and what the base had to gain for it; the base never ships that composition as its only way. The base is the engine, not the game.
5. **Reduce load.** {#reduce-load} Ask only at genuine choice points, with a recommendation; carry the rest. The author should leave each exchange with a clearer idea of their own application, not with homework about the principles.
6. **Only the author's words close a decision, and the record says how it was made.** {#authors-words-decide} An entry waiting on the author (an open item, a gap, a provisional section) closes only with the author's words, quoted and dated (`decided: "<words>" (the author, <date>)`); another agent's conclusion adds a recommendation and leaves it open. Asking, the orchestrator quotes what was built, with its code reference, rather than paraphrasing it. A decision accepted without specifics ("ok, as recommended") is recorded as **decided on the recommendation**, keeping what the author was shown: the choice, the alternatives not taken and the reason, a line each, in the design or entry it closes and in the session record. Why: such a decision stands but is the cheapest to revisit, revisiting needs the alternatives, and it lets a batch be accepted whole.
