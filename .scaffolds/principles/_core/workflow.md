# Workflow rules {#workflow-rules}

Agent context and specs, design/plan/implement, iteration, and keeping design, spec and code honest.

## In brief

One line per section; read the section before acting on it.

- **Context** (§agent-context): the principles are the source; `AGENTS.md` binds code to them, `_spec/` mirrors the
  code; load only your slice; agent context is never auto-formatted; nothing committed names a local path.
- **Design first** (§design-plan-implement): research precedents, surface tensions to the author, agree a design in
  `.design/<area>/<topic>.md`; then plan, loop and `state.md` in `.execution/<work-id>/`, committed with the work and
  never cited from outside.
- **Close a piece of work** (§reconcile-before-merge): fold what it taught into designs, spec and issues (through the
  self-check when the principles change), then close the work folder: it stays as the work's archive, never edited.
- **Records** (§permanent-record): a record in `.records/<work-id>/` at every sitting, compaction or handoff, never
  edited after; the record is cited, the archive beside it is not.
- **Lanes** (§lanes): reuse the agent that holds the context; one lane per worktree, a brief that names model,
  effort and every check; green is an exit code
  with tests run; lanes don't loosen checks, write the work folder or stage the lockfile; the orchestrator merges one
  lane at a time and gates between.
- **Iteration** (§iteration): prototype often, outside the main code, each under its own scope; the author uses it before it ends, and it ends with residuals; a finished prototype is frozen.
- **Drift** (§recursive-loop): disagreement is information; triage it, write a drift note, never bend either side
  silently; design changes are the author's call (§upward-authority).
- **Agreement** (§gaps-queue, §shared-ownership): building must not outrun agreement; the three gap lists are shown at
  every gate; contributors own what they touch, and agreement is emergent.
- **Proof** (§green-is-exit-code): a report, yours or an agent's, is not proof; re-run its checks.
- **The author** (§author): start from their words, reconcile rather than correct, ask only at real choice points
  with a recommendation; only the author's words close a decision, and one accepted as recommended keeps its
  alternatives (§authors-words-decide).

## Codebase structure and agent context {#agent-context}

1. **These modules are the source of the principles.** {#rules-are-source} Skills load them for agents; a project may render them as docs for people. Nothing else restates them.
2. **AGENTS.md** {#agents-md} files (multiple, nested) bind a specific codebase to the principles: module map, build/test scripts, local conventions.
3. **`_spec/` folders hold a semantic mirror of the code** {#spec-folders} (global at the repo root, local per module), so agents can query meaning without reading everything. The spec describes the code *as it is*; intent lives in `.design/` (§design-plan-implement). **Spec = map, code = territory**: when they disagree, that is a signal to triage (§recursive-loop), not a verdict. Registries (commands, error codes, concepts) are the machine-readable part of the spec; `_spec/` links to them instead of copying them. → [§spec-mirror](patterns/spec-mirror.md)
4. **Context is a budget.** {#context-budget} AGENTS.md files and spec entries stay short. An agent loads the slice it needs: the principles README, the modules for its area, the module's AGENTS.md and `_spec/`, and the relevant registries.
5. **Agent context is never auto-formatted.** {#no-auto-format} `.principles/`, the instance folder (`.<instance>/`: its skill, manifest, modules and designs), `.design/`, `.sources/`, `_spec/`, `.execution/`, `.records/`, skills (`.agents/`), `AGENTS.md` files, and any other folder a project keeps plans, progress notes or session records in, are excluded from every formatter and linter. The one exception is the package's checks, `.principles/_checks/*.ts`: they are code, linted and type-checked as code. Agents load and edit these files; a tool that rewraps or reorders them produces diffs nobody wrote, makes what an agent already read stale, and churns reviews. Whoever writes them keeps them tidy.
6. **The codebase is machine-invariant.** {#machine-invariant} Nothing committed names a path on one person's machine: no home or temp folder, no drive path, in code, docs, principles or skills alike. References point inside the repository by relative path, at a published location (a repository URL), or name the thing in words; material from elsewhere that a document relies on (a screenshot, a reference) is copied into the repository beside it, sized for review. This holds for the work folder too (`.execution/`, committed and kept, §permanent-record): a lane's worktree is named by its relative place or its branch, a scratch folder in words. Local scratch files that tools and tests write (databases, run outputs, eval results) go in a gitignored `.tmp/` at the repository root, never beside the sources or at the root itself, and committed files never refer to what is in it. The path check (`_checks/paths-check.ts`) enforces this in the gate.

## Design, plan, implement {#design-plan-implement}

Three kinds of files, with different lifetimes (→ [§workflow-files](patterns/workflow-files.md)):

| Folder | Holds | Lifetime | Tracked |
|---|---|---|---|
| `.design/` (global, root) | what we intend and why: decisions, rejected alternatives, invariants; a folder per area, one file per topic (`.design/<area>/<topic>.md`); designs of prototypes in `.design/_prototypes/<name>/` | durable | yes |
| `_spec/` (global + local) | what the code is (§spec-folders) | durable | yes |
| `.execution/<work-id>/` | plan, checklist, loop, state, drafts, briefs, drift notes, followups: the working memory of one piece of work, and after its close the archive of how it went | edited while the work runs; after the close kept, never edited | yes, never cited (§execution-unreferenced) |
| `.records/<work-id>/` | one record per execution session: asked, decided, delivered, learned, left open (§permanent-record) | permanent | yes |

1. **Design before implementing** {#design-first} for most functionality (trivial changes exempt). The agreed design is a short markdown file in `.design/<area>/<topic>.md` (global only): a folder per area, one file per topic in it. It has no status field: if it is in `.design/`, it is agreed, except a section marked as spelled while building and provisional (§gaps-queue); drafts live in `.execution/` until then. A prototype's designs live under `.design/_prototypes/<name>/`: they are agreed for the prototype and record what it explored, and the product built later will differ (§iteration). Keep it current by editing it in place (git keeps the history); when it stops being true, update or delete it.
2. **Look for precedents before designing.** {#precedents} A design starts from research, sized to the decision: how this problem was solved before, in this codebase (its designs, records, residuals and code), in the sources the principles draw on (§sources), and outside (libraries, other projects, papers, standards). The design names the precedents it builds on or departs from, with links and one line each on what was taken and what was not; a decision with no precedent says so. Research notes live in `.execution/<work-id>/` while the work is in flight; external material worth keeping becomes a source (`.sources/<name>/`).
3. **Surface tensions to the author; don't resolve them silently.** {#surface-tensions} A tension is any place where two things the design must respect pull apart: the author's words and a principle (§reconcile-dont-correct), two principles, a precedent and this codebase, the design and existing code, or a cost against a benefit. Each one is written down explicitly, with the options and a recommendation, and brought to the author at the point it matters (§reduce-load), not buried in a decision. A tension that clarification doesn't dissolve is worked through the four-step check (§self-check). The design records how each was settled, and one still open stays visible as undecided (§four-outcomes) rather than built over.
4. {#plan-and-checklist} Once the design is agreed: write a **plan + checklist** in `.execution/<work-id>/plan.md`. Review, integration and merge gates are checklist items. The plan includes a **testing strategy** (see the testing module, if used).
5. {#loop-file} Once the plan is agreed: write a **loop file** (`.execution/<work-id>/loop.md`) that governs implementation. The loop uses the testing strategy to decide what to run when (targeted, then the gate).
6. **The loop maintains `state.md`**: {#state-file} a concise description of where the work stands (done, in progress, next, blockers, decisions taken, how to verify, anything surprising). It is updated at every meaningful step and before stopping, so a different agent can pick up the work cold (budget or token exhaustion, crash, handoff). The loop's first instruction is to read `state.md`.
7. **`.execution/` is never referenced from outside itself.** {#execution-unreferenced} No code, spec, design, test, comment, commit message, record or doc may link to or depend on a plan, loop, state, draft or brief. Anything worth keeping must live in a durable place: what is true in the design, the spec or the code, how it went in the record. The folder is committed and kept (§permanent-record), but as evidence, not as a source: it is found by its work id (the name its record folder shares), never by a link, so nothing that is read as true can rest on a plan that was never agreed. Files inside the folder may refer to each other.
8. **Reconcile, then close.** {#reconcile-before-merge} An execution folder is fully reconciled before the work it holds is called done (and before the merge that ends it), then closed (§permanent-record):
   - decisions and rationale → `.design/` (edited in place, §design-in-place);
   - what the code now is → `_spec/` and the code itself (tests, comments, AGENTS.md as appropriate);
   - drift notes → resolved, or turned into followups (§drift-notes);
   - **followups** → issues (§followups); none may survive only in `.execution/`;
   - **a fold-back** (what the work taught, turned into changes to the principles or designs) → run the self-check on it (§self-check, the `principles-self-check` skill) and record its delta in the session record.
   Closing it: resolved drift notes are deleted (git keeps them), `state.md` ends with a line saying the work is closed, on which day and in which record, and from then on nothing in the folder is edited. A later session on the same work opens a new work id or reopens the folder by a new section in `state.md`, never by rewriting the old ones. The merge gate checks: no tracked file outside the folder refers into it, and nothing in it names a local path; the finalize check, that the checklist is complete (or its open items listed as followups) and no drift note is open.
9. **Followups.** {#followups} Work discovered but out of scope is never left as a TODO in code or buried in a plan. Each becomes an issue in the tracker (or wherever the project's manifest says its open items go), stating the context, why it was deferred and what done looks like (rough design thinking goes in the issue, not in `.design/`). Small cleanups go in the current work instead if cheaper than recording them. In a prototype, followups are its residuals instead (§residuals).
10. **Handoff across machines/worktrees.** {#handoff} The work folder travels with the work branch: commit it (the orchestrator does, §lanes-report-not-write) and push, and the receiving agent starts from `state.md`. Uncommitted state is lost at a handoff, so `state.md` is committed before stopping.
11. **Every execution session leaves a permanent record, and the work folder is kept beside it.** {#permanent-record} Each session leaves a short record in `.records/<work-id>/<date>-<name>.md` (a session that spans several sittings, a compaction or a handoff writes one at each, not only at the close): what the owner asked, what was decided (with "don't reopen" where they said so), what was delivered and how it was verified (a compact ledger: commits, tests, review findings), what was learned, and what was left open. Decisions are also copied into the design they belong to, so the design says what is true now and the record says how we got there. Records are never edited afterwards. Code may cite a design or a record; it never cites a plan step. The work folder is not deleted: once closed (§reconcile-before-merge) it is the work's archive, the plans, drafts, briefs, gap lists and state the record summarizes. The two do different jobs: the record is short, reviewed and cited, what a reader needs; the archive is complete and never cited, what a later fold-back or self-check needs as evidence (which alternatives a draft weighed, which findings each lane's review raised, what a plan expected against what was built), and nothing else can restore it. The archive holds what the process wrote, sized for review: text, and small scripts that made one-off edits; generated output (screenshots, run logs, databases, eval results) stays in `.tmp/` (§machine-invariant), and a screenshot the record relies on is copied beside the record. The record's template: [§workflow-files](patterns/workflow-files.md#session-record-recordswork-iddate-namemd).
12. **Vocabularies are written down before they are built on, and then kept stable.** {#stable-vocabularies} There are two kinds, and they are rarely the same. A **code vocabulary** is what other code, stored data and agents speak: a representation's node kinds and text form, a small language (queries, a history), a public API, the names of commands and addresses. A **product vocabulary** is what people read and say: the words on screens, in notices and in the assistant's answers. Each is designed and reviewed in its own right, and the mapping between them is written down (which code term each product word shows, and where one shows several or none); a code term never reaches a screen just because it exists, and a product word never renames code just because people say it. Each new vocabulary is written down (its terms, a sample written in it, what it leaves out) before anything builds on it: a code vocabulary once it works headless (before screens, agents, other lanes or stored data use it), a product vocabulary before the screens that speak it. The depth is sized to the work: in a prototype a short list is enough and the author need not review it, since what matters is that it holds still; in the main codebase the author reviews it at a gate in the plan. From then on, either changes only as a design change brought to the author, a code vocabulary carried by a migration or a deprecation, never by a quiet rename. Why: a code vocabulary spreads into every consumer, stored document and prompt, so a late change is a migration everywhere; a product vocabulary is what people learn, so a change costs them; and the two pull apart because code needs precise, composable terms and people need familiar ones. Both are where the author's terms (§authors-words) land. It extends §name-the-roots from the root nouns to the whole surface.

## Lanes {#lanes}

Running work in parallel: lanes in worktrees, an orchestrator that merges, briefs that carry everything a lane needs ([§workflow-files](patterns/workflow-files.md#lane-brief) has the brief).

1. **Parallelism**: {#parallelism} decide what can run concurrently, sized to machine capacity. Default to 1-2 *heavy* lanes (builds, gate runs, long agent work) and 1-2 *light* lanes (reviews, quick tests, spec updates), so heavy work never starves quick feedback. Remote/cloud offload is more lanes, not a different model. `state.md` shows what each lane is doing. Each worktree gets its own dependency install, its own ports for anything it serves, and its own scratch under `.tmp/` (databases, run outputs), so lanes never collide on a shared one.
2. **Reuse agents that already hold the context.** {#reuse-agents} A follow-up on work a subagent did (a fix after its review, the next step of its task, a question about what it found) goes back to that subagent, which still holds the files and reasoning, instead of a new one that must rediscover them. Start a fresh agent only for independent work, when fresh eyes are the point (a review not anchored on the author's view, §upward-authority), or when the old context is exhausted or misleading. The loop file (§loop-file) records which agent owns which task, and roughly how much context it holds, so it can be continued, or replaced before its context is too large to be reliable.
3. **Match the model to the task.** {#model-per-task} Routine, well-specified implementation, scaffolding, tests and mechanical edits run on a fast, cheaper model; design, reconciliation, review and anything ambiguous run on the strongest model. The plan, and each lane's brief, names the model tier and the reasoning effort per task (scaffolding and mechanical edits on a fast model at low effort; design, review and ambiguous work on the strongest at high effort), and a task that turns out ambiguous is escalated rather than guessed through.
4. **Name the root nouns before fanning out.** {#name-the-roots} The gate that agrees a design's map names its root concepts (what the top of the state is called, the core kinds) before parallel lanes start, and asks the author when a name is not obvious (§design-first, §surface-tensions). Why: a name changed after lanes have spread it is a rename across every lane and every merge.
5. **Commit often; parallel writers work in worktrees.** {#commit-often} An agent commits whenever it reaches a small green step (it builds, a test passes, a check works), so nothing is lost and the history shows how the work went; each commit stages only that agent's files. Lanes that write in parallel each work in their own git worktree on a lane branch cut from the work branch, so they never touch one checkout; a lane that only reads, or the only writer at the time, may work in the main checkout. When a lane is finished, the orchestrator verifies it (§upward-authority), merges its branch into the work branch, then removes the worktree and deletes the lane branch; no finished lane's worktree is left behind. Lane agents commit only on their own branch; the orchestrator does every merge, both ways (bringing the work branch into a lane, and a lane into the work branch), because it holds both sides' context. Before fanning out, the orchestrator names the files each lane will touch: lanes that share a hot file (a central registry, a catalog, the agent runner, the composition root) are serialized, or the file is first split so each feature registers itself. A clean textual merge is not proof: when two lanes changed what a shared function means, the merge runs the other lane's tests and checks too. Shared status documents and version lines are hot files too (as the lockfile is, §orchestrator-owns-lockfile): a lane writes what it moved as an entry of its own (a changelog entry per lane) and states the version bump it needs; the orchestrator folds the entries into the status document and sets the version at the merge, in a commit of its own. A helper two lanes need is named before the fan-out: the first to merge owns it. A lane stops only processes it started and never uses tool state shared across worktrees (the git stash, a shared scratch path); a port in use means another port, not stopping whoever holds it.
6. **Merge one lane at a time, and gate between.** {#merge-one-at-a-time} The orchestrator merges one finished lane into the work branch and runs the full gate on the result before merging the next, so a failure has one cause. It brings the work branch into a lane only at a stop the lane has reported, never while the lane's agent is mid-step, because the merge changes the checkout under it. It keeps reports and exit codes in its context, not diffs: its context is the bottleneck of a fan-out.
7. **The orchestrator owns the lockfile and other generated shared files.** {#orchestrator-owns-lockfile} A package manager's lockfile (`pnpm-lock.yaml`, `Cargo.lock`, `uv.lock`) is always a hot file (§commit-often), and so is any file generated from many packages at once (codegen output, export indexes, aggregated registries): a lane declares the dependencies it needs in its package's manifest, may install locally to run its checks, and never stages the lockfile or a generated shared file; the orchestrator regenerates them once at each merge and commits that alone, and the gate installs from the lockfile without changing it. Why: every lane that adds a dependency rewrites the same file, so lane lockfiles conflict or arrive half-updated, and a merged lockfile nobody regenerated can name what no manifest declares.
8. **A lane doesn't loosen its own checks.** {#lanes-dont-edit-checks} Tests, snapshots, ratchet baselines, guard thresholds, and lint, formatter and gate configuration are hot files for every lane: a lane that needs one changed stops and reports why, and the orchestrator decides with the author (§refusals-to-author). The lane's report lists every assertion it deleted, skipped or weakened. Why: exit codes are only as honest as the checks behind them, and the quickest way to a zero exit is to weaken what produces it.
9. **A lane reports; it doesn't write the work folder.** {#lanes-report-not-write} The work folder is the orchestrator's: a lane's worktree has only the copy from when its branch was cut, so the lane gets its brief in its instructions, and its drift, gaps and followups come back in its report, which the orchestrator files in `drift/` and the gaps lists. Why: every lane writing the same `state.md` and gap lists makes them hot files that conflict at every merge, and a lane writing its stale copy, or another checkout, works behind the orchestrator's back.
10. **A lane's brief names every check its area requires.** {#briefs-name-checks} Not only its package's tests: the guards the touched area's rules demand (a scaling guard for a bulk path, an allocation guard for a hot one) and the repository-wide checks (dependency boundaries, exports, the principles' id check), and the lane runs them before it reports. A report that omits one is not green (§plan-and-checklist). The gate is one committed script (an entry-point task) the lane runs, not a list each lane transcribes, so adding a check is one edit. A lane's report also names what it left out, refused or fell back on, each path with its code, and a reviewer's brief lists the review's finding classes as its checklist. The brief's shape is in [§workflow-files](patterns/workflow-files.md#lane-brief). Why: what the brief does not name the lane does not run, and a review or a merge finds it later at a higher cost; a gate copied into each brief drifts with each copy; and a path a report doesn't mention is a path a reviewer has to find.
11. **Green is an exit code.** {#green-is-exit-code} A step is green when its checks exit zero, each run as its own command whose status gates the commit, and the run executed a non-zero number of tests with no new skip or focus marks (a filter that matches nothing exits zero too); never when a filtered view of their output looks right (a search for a summary line succeeds whatever the tests did). Why: a pipeline's status is its last command's, so a commit chained after one lands on a failure.
12. **A refusal by the permission system is the author's call.** {#refusals-to-author} A lane whose action the agent permission system refuses (an edit to configuration, a lint or architecture rule, credentials) stops that step and reports the action and its reason; the orchestrator brings it to the author with a recommendation and never performs it on the lane's behalf, and no other agent's message counts as the author's approval (§upward-authority). Why: a refusal marks where a person decides; doing it one level up launders it.

## Iteration {#iteration}

1. {#prototype-often} Prototype often; do not fear rewrites.
2. {#prototype-outside} Prototype **outside** the main codebase, then port the validated design in. This does not conflict with §design-plan-implement: the prototype is how the design gets validated, and its output feeds the design. Prototypes live in `prototypes/<name>/` at the root, outside the build; for UI, a reference package (`prototypes/<design>-reference/`) shown in the project's component workbench (its reference section) is the prototype space.
3. **A prototype ends with residuals, not with everything resolved.** {#residuals} What it leaves for the next iteration (open drift, followups, known bugs, limits) is listed in its nested `_spec/residuals.md`, one line each, grouped and cited, instead of being filed as issues or fixed before it ends; what it taught goes into the principles and its designs (§reconcile-before-merge, §gaps-queue).
4. **Prototypes don't share a namespace, and a finished one is frozen.** {#frozen-prototypes} Each prototype names its packages under its own scope (`@scope-<prototype>/...`), so two prototypes never collide in one workspace and a new one reuses an earlier one's code by forking it, not by importing it; promotion into the main codebase renames the scope. Only work in flight is gated: once a prototype has ended (its residuals written), it is frozen, its tests leave the gate and run on demand, and it is kept only as far as it still builds. Nothing in flight depends on a frozen prototype.
5. **A prototype is used by its author before it ends.** {#used-before-done} The plan's last gate before the close is the author using the prototype as its people would (signing in, asking, clicking through the screens), on real data, with the agent standing by to fix what they find; tests and an agent's own checks in a headless browser come first, not instead. What the author finds is fixed or listed in the residuals before the close, and goes into the principles if it is general. Why: what matters in use (a code term on a screen, a line that reads as broken, motion that feels wrong) passes every test written from the design, because the tests share the design's blind spots.

## Iterating on architecture, design and spec (the recursive loop) {#recursive-loop}

Principles, architecture, design, plan and code form a stack; `_spec/` describes the code layer. Each layer is a *hypothesis* about the layer below and a *constraint* on it. Truth about **what runs** is the code; truth about **what we intend** is the highest layer a human has agreed. When they disagree, neither side wins by default. → [§drift-triage](patterns/drift-triage.md)

1. **Disagreement is information.** {#disagreement-is-information} Never silently bend code to match a design, and never silently edit a design or spec to match code. Both skip the question of which one is wrong.
2. **Triage every drift into one of four outcomes:** {#four-outcomes}
   - **Code is wrong**: the design states intent we still hold. Fix the code.
   - **Spec is stale**: the code is right and the spec lagged. Update the spec in the same change.
   - **Design is wrong**: following it produces bad code (awkward, slow, leaky, repeated workarounds). Change the design, then the code. This goes through §design-plan-implement at the size it warrants.
   - **Undecided**: do not guess, and do not build further on the contested point; if it outlives the work, it becomes a followup issue (§followups).
3. **Bending signals.** {#bending-signals} Evidence that the design should bend, not the code: the same workaround appears 2-3 times; a port needs an escape hatch that exposes a provider; tests need mocks of internals instead of ports; an invariant is violated by every real caller; a plan step cannot be written without contradicting the design.
4. **Stop and write a drift note.** {#drift-notes} An agent that finds the design or architecture blocks a correct solution stops, writes a short drift note (what, evidence, proposed outcome) in `.execution/<work-id>/drift/` (a lane puts it in its report instead, §lanes-report-not-write), and continues on unaffected work. It may not land code that contradicts an agreed design until the note is resolved. **Drift notes are working notes, not results**: a resolved note is deleted from the folder (git keeps it, and the archive keeps none open, §reconcile-before-merge); the durable result is the fix itself (code, spec entry, or the in-place design edit with the evidence in the commit message, §design-in-place). A note that cannot be resolved within the work becomes a followup (§followups).
5. **Design changes go through the author.** {#upward-authority} Agents may fix code and update stale spec entries freely (outcomes 1, 2). Changing design, architecture, ports or principles (outcome 3) is the call of the author the agent works for: the agent brings the evidence and the migration plan, and the change lands when that author contributes it. There is no further sign-off (§shared-ownership).
   A subagent's or reviewer's report is not proof: the checks it claims are re-run before its conclusion is acted on. Nor does it close a decision: only the author's words do (§authors-words-decide).
6. **Recursive scope.** {#recursive-scope} The same loop applies at every level: code vs design, design vs architecture, architecture vs principles. A drift is resolved at the lowest level that can absorb it; if it cannot, escalate one level up. These rules change the same way: evidence from real work, then a human decision.
7. **Rewrites are the loop working.** {#rewrites} When repeated bends accumulate, re-derive the design from what the code taught us (§iteration), then replace the stale parts rather than patching around them.
8. **Update the design in place.** {#design-in-place} An outcome 3 change edits the affected `.design/` document directly, and the commit message carries the evidence and what was rejected. If the reason is non-obvious to future readers, add it under the design's "rejected alternatives". Git history explains how we got here; there is no separate log or notes folder.
9. **Drift is checked mechanically.** {#mechanical-drift-checks} Before merge, the local finalize step fails while `.execution/<work-id>/drift/` holds any note. At the gate (see the testing module, if used), the merge gate rejects any reference into `.execution/` from outside it, and the drift check verifies that `_spec/` links and registry references (commands, error codes, concepts) still resolve, and reports spec entries whose code changed without them (to update in the same change or record as a followup issue): a package whose source changed while its `_spec/` did not is a warning in the report, not a failure, since most code changes need no spec change. An index page (of languages, designs, recipes, runtimes) is generated from, or tested against, what it lists, never kept by hand, and a page's facts (a version, a list of kinds) are read from the source. Why: each lane keeps its own spec true, but index pages and facts copied into docs fall behind at the scale of a whole round.
10. **Building must not outrun agreement; the gaps are a visible queue.** {#gaps-queue} With agents, implementation is faster than authors can agree to what it decides, so incoherence collects in three gaps: *built but not agreed* (open drift notes, deviations from sketches, fixes to stable patterns awaiting the author's decision), *agreed but not built* (followups, plan items) and *built but not adopted* (prototype lessons not yet folded back into the rules and patterns). Each gap is a list the orchestrator keeps current and shows at every gate, before any demo, compact enough to decide on (one line per item, grouped, with a recommendation). A lane does not build further on a point that is waiting in the first gap; when that gap grows faster than it is decided, work slows to the pace of agreement rather than piling up undecided choices. A lane that builds differently from an agreed design writes it in that design's "Spelled while building (<lane>, <date>; provisional, for the author)" section and nowhere else in the design; the author's decision rewrites the marker with the date and the author's words (§authors-words-decide), and every marker still provisional is listed in the first gap at each gate. Why: a deviation recorded only in the work folder is invisible to whoever reads the design, while one written into the design's body passes for agreed; a marked section is a status, but scoped, so everything outside it stays agreed.
11. **Contributors own what they touch; agreement is emergent.** {#shared-ownership} No module, pattern or design belongs to a person, and there is no sign-off role. `main` is what authors contribute: whoever changes something owns that change, keeps it consistent with the rules and designs around it, triages the drift it causes, and takes up the "To decide" items it touches; agreement emerges from what authors build on, change or revert. A source names where material came from, not who controls it. An agent works for an author, the person who asked, and brings what needs a person's decision to that author (§upward-authority).

## Meeting the author where they are {#author}

The person who brings an idea is the author of the application, not a client of the principles. Agents help them turn their ideas into a good application in their own terms, and use the principles as the means, not the subject.

1. **Start from the author's words.** {#authors-words} Capture the idea in the author's vocabulary and structure first (a doc, a sketch, a list of wishes), keep it as the reference, and translate it into the principles' terms second. A translation that loses something says what it lost.
2. **Reconcile, don't correct.** {#reconcile-dont-correct} Where the idea and the principles disagree, show both sides and the options: often the principles have a primitive the idea needs, sometimes the idea shows a gap in the principles (§recursive-loop), and sometimes it is a genuine choice the author makes. A reconciliation is a document of its own, kept beside the idea, not a rewrite of it.
3. **Keep a model of the author, labeled as one.** {#author-model} Agents keep an explicit, inspectable model of the author's intent: goals, decisions already made, preferences, recurring corrections, vocabulary. It is owned and correctable by the author, says where it is uncertain, and is used to propose, never to decide: when the model and the author disagree, the author wins and the model is updated.
4. **Separate what belongs to the application from what belongs to the base.** {#application-vs-base} Application semantics live with the application (`.sources/<name>/`, see the [sources pattern](patterns/sources.md)); only what several applications need, or what an application cannot build on top, becomes a base primitive. Each application is also a test of the principles: its reconciliation lists what the base already offers, what it lacks, and what was deliberately left to the application.
5. **Reduce load.** {#reduce-load} Ask only at genuine choice points, with a recommendation; carry the rest. The author should leave each exchange with a clearer idea of their own application, not with homework about the principles.
6. **Only the author's words close a decision, and the record says how it was made.** {#authors-words-decide} An entry waiting on the author (an open item, a gap, a design's provisional section) is closed only with the author's words quoted and dated (`decided: "<words>" (the author, <date>)`); a reviewer's or another agent's conclusion adds a recommendation and leaves it open. Asking, the orchestrator quotes what was built with its code reference instead of paraphrasing it. A decision the author accepts without being specific ("ok, as recommended") is recorded as **decided on the recommendation**, apart from one the author spelled out, and keeps what the author was shown: the recommended choice, the alternatives not taken and the reason given, a line each, in the design or entry it closes and in the session record (the draft that weighed them stays in the work folder, §permanent-record). Why: an author often decides with too little time to weigh each choice; such a decision stands, but it is the cheapest to revisit, and revisiting needs the alternatives without reconstructing them from a transcript. It also lets a batch be accepted whole, since nothing is lost by it.
