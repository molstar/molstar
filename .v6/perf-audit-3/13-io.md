# Slice 13: io (v3)

Scope: `packages/io`: text CIF byte tokenizer (`cif/text`), `TextByteTokenizer` and the text formats on it (GRO, XYZ,
SDF/MOL, MOL2, PSF, LAMMPS data and dump, cube, DX, OBJ, PLY, PRMTOP, TOP, TBL, XSC), CSV (RFC 4180), BinaryCIF
(MessagePack, lazy/fused/Float32/dictionary decoding), plus the shared helpers they use in core (`util/utf8.ts`,
`util/number-parser.ts` byte parsers, `util/zip` gzip). v2 did not audit io (profiled only) and kept LAMMPS notes in
[13-lammps-large-text.md](../perf-audit-2/13-lammps-large-text.md); this is the first audit of the slice.

HEAD `16277d822`, A/B base `0944823d4` (the v2 base extracted in `pa3/00/base`). Node 26.12, Apple M4. The machine
was very loaded during the runs (load 14–28, 13.4 GB swap in use): wall times below are ranges and only same-process,
interleaved A/B ratios are meaningful; memory is `heapUsed + arrayBuffers` after a full GC and a 50–200 ms wait,
allocation is `total_allocated_bytes` (JS heap only: typed-array stores are not in it). Scratch:
`pa3/13/` (`driver.mjs` loads the base and the HEAD bundles into one process and alternates them).

PRs since v2 that touched the slice: #2036 (CIF parser pass: byte tokenizer, lazy/fused/Float32/dictionary BCIF),
#2039 (text CIF from bytes, gzip by its bytes), #2040 (text formats from bytes, `TextByteTokenizer`, CSV RFC 4180),
#2035 (ajax by fetch; core), #2042 (CIF flatten once), #2037 (LAMMPS periodic images), #2044 (small fixes).

Decode results equal base: every value of every field (`str` + `valueKind`, plus `int`/`float` in the edge set) hashes
the same on 7qpd (427,890 values), flat-192.cif (29.1M), flat-32.bcif (4.87M, all categories) and flat-192.bcif
(29.1M, `atom_site`); 35 hand-written text CIF edge cases (CRLF, CR, UTF-8 multibyte in plain/quoted/loop values,
`;` fields with CRLF and trailing newlines, unterminated quotes and `;` fields, triple quotes, 254/255/256-byte values
in singles and loops, loop growth with long values, `data_` inside a loop, save frames, numbers) are identical to
base, synchronous and with chunked parsing (`run(observer, 0)`, chunk boundaries everywhere, 300k-row loop), except
the documented changes: a UTF-8 BOM now parses (base: "Unexpected token"), a lone surrogate becomes U+FFFD, and
`loop_` without names is a `ReaderResult` error (base threw a `TypeError`).

### P1: MessagePack `bin` byte loop

`bin` allocates `new Uint8Array(length)` and copies with a JS loop; the comment argues against `subarray` (views),
but `state.buffer.slice(o, o + length)` is a native copy into a fresh buffer (byteOffset 0, which `decoder.ts`'s
`view(data.buffer)` needs). Probe `pa3/13/msgpack.mjs` on the 349 blobs of flat-192.bcif (19 MB): loop 82–152 ms,
slice 1–12 ms over 5 rounds; the whole `decodeMsgPack` of the file is 62 ms with the loop. Same for flat-32 (3.2 MB):
6–64 vs 0.4–1.1 ms. The BCIF parse stage is mostly this copy now that decoding is lazy. Fix: `slice`. Unchanged since
v1.

### P2: LAMMPS dump token stores

`handleAtoms` makes `id`, `mol`, `type`, `x`, `y`, `z` (and `ix iy iz`) start/end token arrays for every frame
(`count * 2` Uint32 each) and keeps them in the parsed `LammpsTrajectoryFile`, a state object; `coordinatesFromLammpsTrajectory`
(model) then makes Float32 frames. Probe `pa3/13/lammps.mjs`, 100k atoms × 20 frames: tokens 47.5 B/atom-frame
(71.5 with images), coordinates 12.3 (24.3). Fix (L5 option 1): parse x/y/z (and images) straight into Float32 per
frame and ids, mol and type once from frame 0; a lazy frame index (option 2) removes the per-frame parse peak.

### P3: PDB on the string tokenizer

The plugin decodes PDB to a string (`SO.Data.readText`), then `Tokenizer.readAllLinesAsync` (string), and
`model/formats/structure/pdb/*` reads substrings. Probe `pa3/13/pdb.mjs` (synthetic 500k ATOM lines, 39 MB): line
split 97–110 ms over the string vs 52–54 ms with `TextByteTokenizer.readAllLinesAsync` on the bytes; parse +
`pdbToMmCif` 412–454 ms. Above 512 MB the string is a `ChunkedBigString` (2× slower scan, and it slows the same call
sites for small files after: v2 L-notes) and past 4 GiB the offsets wrap (B2). Moving PDB to bytes needs
`pdb/to-cif.ts`, `atom-site.ts` and friends in model (slice 04) on byte tokens.

### P4: short ASCII strings by concatenation

`utf8ReadValue` → `shortAscii` handles 0–4 bytes with one `String.fromCharCode` and 8 with one, but 5–7 bytes go
`ret += 4 chars` + `ret += 1 char` ×1–3, each step a new flat string (V8 flattens below 13 chars), and 9–24 bytes
build cons strings. Probe `pa3/13/ascii.mjs`, 1M distinct values: 5 bytes 48 B and 136 ms → 24 B and 43 ms; 6: 72 B
116 ms → 24 B 43 ms; 7: 96 B 152 ms → 24 B 75 ms (a `switch` with `fromCharCode` of 5, 6, 7 arguments). For 9–24
bytes `fromCharCode.apply(subarray)` is worse (248–352 B); keep the loop there or try a two-call split. Where it
hits: text-CIF `str` of unique values (flat-192: `id` 86 MB vs base's substrings 34 MB, `Cartn_x` 102 vs 34 MB,
`B_iso_or_equiv` 56 vs 34; 1.5–2.6× slower), CSV, GRO/XYZ/SDF names of 5+ chars. Not the mmCIF model build: its
`atom_site` `str` reads are 1–3 bytes (probe `pa3/13/reads.mjs`: `label_atom_id` 1.78 reads/atom, avg 1.3 bytes).
Repeated short values got cheaper (cache: `label_comp_id` 9 vs 34 MB).

### P5: `ByteTokens` growth cap

`estimateLoopRows` caps a step at 4× the current room so a small loop near the top of a big file does not reserve the
file; `atom_site` of flat-192 grows 32 → 52 → 84 → 336 → … → 344k → 1.17M rows (~9 steps), each a zero-filled
Uint32+Uint8 pair and a copy (~208 MB allocated for 152 MB kept). CPU profile of three parses: `grow` 11 % of self
time (inflated by page faults on the swapping machine). Fix: let the step reach the estimate once the loop has read
enough rows (say 4096) for its density to be reliable, keeping the 4× cap below that.

### P6: CSV token reservation

`rowEstimate = data.length / (first record bytes)`, capped at 1M rows, reserves `2 * rowEstimate` Uint32 per
column up front and never trims. A short header over long rows over-reserves by the length ratio (3.3× for `x,y,z`
over `12.3456,23.4567,34.5678`), up to 8 MB per column, retained with the file. Fix: estimate from the first data
record (or the first 64), or trim at the end.

- **B1**: probe `pa3/13/gz.mjs` (base and HEAD alike): two concatenated members. `ungzip`'s stream path refuses the
  declared size (ISIZE of the last member), `ungzipBlocks` then inflates from the first header to the end with
  `deflate-raw`, which fails on the second member. Fix: loop members in the fallback, or a `DecompressionStream('gzip')`
  without the size cap (it reads multiple members).
- **B2**: by code: `Tokenizer`/`TokenBuilder` offsets are Uint32 and `ChunkedBigString` maps index → chunk by
  `>>>`; the byte readers refuse, the string path does not. Not probed (needs a 4 GiB input). Fix: P3, or the same
  `checkLength` on `data.length` in `readAllLinesAsync`.
- **B3**: probe `pa3/13/case.mjs` on flat-32.bcif: `same field object false | same decoded array false`. Fix: cache by
  `col.name`.
- **B4**, **B5**: by code; both are behaviour changes of the byte port, rare inputs.

## Already good, re-checked

- Text CIF byte tokenizer: equal to base on all real and edge inputs above, chunk boundaries included; error lines
  equal; 4 GiB guard; tokens 5 B/value (147 MB on flat-192.cif); values decode to fresh strings, so read values no
  longer pin the source (base's ≥13-char substrings pinned the whole text).
- `ByteStringCache`: zero-length and short keys correct (the initial `''` slot only matches length 0); turns off on
  unique columns.
- BCIF fused decoder: chain coverage and wrap semantics match the step decoder (read against `decodeStep`); masked
  dictionaries fall back to arrays.
- CSV (RFC 4180): 20 cases (CRLF inside quotes, doubled quotes, trailing delimiter, short/long records, BOM, CR-only,
  empty lines, unterminated quote and text after a closing quote reported with their line, comments, duplicate and
  quoted headers, UTF-8).
- `readResponseBody` (#2035): one buffer for a known length, chunks otherwise; no double copy.
